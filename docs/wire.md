# Desk wire

One wire connects `shuttle mcp` to the daemon, the runtime (`desk.mts`) to the daemon, and the CLI (`shuttle desk VERB`) to the daemon. It is implemented once in `desk_core::wire`.

## Endpoint

| OS | Default endpoint |
|---|---|
| macOS | `~/Library/Caches/loomhand/shuttle/desk.sock`, mode 0600 |
| Windows | `\\.\pipe\loomhand-shuttle-desk-<SID>`, your user's SID such as `S-1-5-21-…-1001`, local clients only |
| Linux | `$XDG_CACHE_HOME/loomhand/shuttle/desk.sock`, else `~/.cache/loomhand/shuttle/desk.sock`, mode 0600 |

`[daemon] socket_group` in `config.toml` opens the macOS or Linux socket to that group: mode 0660, owned by the group ([config.md](config.md#daemon-endpoint)). On Windows the pipe admits SYSTEM and its user, and `socket_group` names one more account or SID that may read and write it. `SHUTTLE_SOCKET` overrides the endpoint for the binary, and the daemon hands its endpoint to the runtime, the plugins and the services in the same variable.

## Framing

- **One call per connection.** The client writes one frame and reads one frame, and keeps its side of the connection open until the reply: closing it, or shutting down its write side, cancels a call the daemon answers itself. A cancelled run is ended as by `safety_stop` (see [`script_run`](#runs): TERM, then KILL 2 s later, on macOS and Linux, or KILL at once when its TERM already went out, as during a timeout's grace; its Job object at once on Windows), and its turn is free at once; a desk action the driver or the accessibility API has already started finishes on its own, as after a stop. A call of a [service plugin](#service-plugins)'s tool is the exception: after its first frame the connection belongs to the service, and a client that closes its side half-closes the connection toward the service instead of cancelling; on Windows, where a pipe has no half-close, the close ends the call.
- **MCP requests.** `shuttle mcp` on stdio reads its client while a request runs and answers requests in order, one at a time. A `notifications/cancelled` drops the request it names, running or queued: the request gets no reply, and a running one closes its connection to the daemon, which cancels the call as above. An MCP cancel of a [service plugin](#service-plugins)'s tool reaches the service on macOS and Linux as a half-close of its connection, and the service ends the call itself when it reads EOF; on Windows, where a pipe has no half-close, it closes both connections. Over HTTP ([README](https://github.com/loomhand/shuttle#over-http)) each connection runs on its own, each `POST` gets its own reply, and a cancel names a request of its own `Mcp-Session-Id`. A call whose answer cannot be read, because the daemon or service closed the connection or sent a frame the reader refuses, comes back as an error that says whether it ran is not known. A call that arrives while the daemon stops answers that nothing ran.
- **Frame:** a big-endian u32 length, then that many bytes of JSON. A frame over 64 MiB is refused.
- **Request:** `{"agent_id": string, "tool": string, "args": object}`; `agent_id` defaults to `""` and `args` to `null`. `shuttle mcp` gives each MCP session an `agent_id` of its own, `mcp-<client name>-<nonce>` on stdio and `mcp-http-<Mcp-Session-Id>` over HTTP, so a session's `web` holds, default computer session and service calls are its own.
- **Response:** `{"text": string, "is_error": bool, "image_b64"?: string}`. `text` holds the result, JSON for the desk verbs; `image_b64` is the image when the call took one: a PNG, or for the [computer calls](#computer-calls) WebP or JPEG. A failure is `is_error: true` with the reason in `text`, never a closed connection.

## Desk calls

Desk calls name `desk_<verb>` tools:

| Verb | Arguments | Result |
|---|---|---|
| `windows` | | the top-level windows: `id`, `title`, `role`, `pid`, `active`, and `app` (the app's name on macOS, the executable on Windows and Linux) when the OS says; on macOS a window also has `bounds` (`[x, y, w, h]` in desk coordinates) and, when its process runs an executable in the `Contents/MacOS` of a `.app` bundle whose file name differs from its `app` name, ignoring case, as on a macOS in another language (`文本编辑` from `TextEdit.app`), `bundle`, that file name without `.app`, and a sheet, also one shown on another sheet, is a `dialog` whose `owner` is the `id` of the window or sheet it hangs on; on Windows a window with an owner window has `owner`, that window's `id`; on Linux a modal dialog the screen does not show also has `modal` (`hidden`, `off the screen` or `behind "TITLE"`) and `blocks` (the title of the window it blocks), and a window of a process that owns a dock or desktop window (`_NET_WM_WINDOW_TYPE`), such as the panel or the desktop, has `shell: true`. A window whose app did not answer the list in time is listed as it was last read, with `stale: true`; `snapshot`, `find`, `at` and `close` on it fail until its app answers. On macOS with background or `auto` input it also lists the windows on another Space, a desktop or a full-screen app's, with `space: "other"`, never active; with background input `snapshot`, `find`, `at` and `close` on such a window fail with "is on another Space", since accessibility reaches it only on the current Space. Optional fields are left out when unknown |
| `unanswered` | | on Linux, the window `_NET_ACTIVE_WINDOW` names when AT-SPI lists no window of its process, as an app that stopped answering accessibility (busy, or blocked in a dialog) leaves it: `title`, `pid`, `role` and `app`, with `id` empty; `null` when there is none, when its app is outside the app allowlist, or on macOS and Windows |
| `wait` | `since` (a `windows` result), `timeout_ms` | `changed` and `windows`: answers once the window list differs from `since`, or with the same list once `timeout_ms` has passed (5 s at most), counting the time spent reading lists, with a last read at the deadline. The macOS and Windows desks check a cheap on-screen window fingerprint every 10 ms and read the full list at once when it changes, and otherwise every 100 ms or the last read's duration, whichever is longer; the Linux and Android desks have no fingerprint and read the full list every 10 ms or the last read's duration, whichever is longer, never sleeping past the deadline; `since` and the list are compared after the app allowlist filters both |
| `snapshot` | `window?`, `pid?`, `id?` (a window id from `windows`, in place of `window`), `keys?`, `menus?`, `urls?`, `bounds?`, `text?`, `max_chars?` (with `text`), `since?` | a window's tree as nodes (`ref`, `id`, `parent`, `depth`, `role`, `name`, `states`, ...; on macOS, Windows, Linux and an Android device a password field's `states` hold `protected`, and an Android one carries no `value`; on Linux a password field is one of AT-SPI role `password text`, which carries no `value`, while a GTK 4 entry that hides its text reports that role from GTK 4.20 on when its input purpose is password or PIN; one that only hides its text reports a plain text box, whose `value` is the masked text from GTK 4.20 on and the clear text before it), or an outline with `text`; on Windows the node of a dialog behind the front window that background keys go to, its thread's keyboard focus, has `keyboard` in its `states`, or the nearest listed ancestor of that element when the element itself is not listed, and no node does when the thread's focus is outside the dialog; a Linux node read with `keys` also carries its raw AT-SPI key binding as `keys`; on macOS the app's menu bar comes with a window only with `menus` (omitted or false: no app menu bar in the snapshot), and other backends ignore it; a tree holds at most 2500 nodes on macOS, Windows and Linux, while an Android tree has no node limit; on macOS, Windows and an Android device it leaves out elements more than 64 levels below the window, where Linux keeps them; with `urls`, a `link` node carries `url`, its target, where the app exposes one (AT-SPI `Hyperlink.GetURI`, macOS `AXURL`, the UI Automation value), in nodes but not in the `text` outline. On Linux `urls` costs one `GetURI` call per link, so at most 2500, about 4 ms for 250 links in Chrome. macOS asks each element for `AXURL` in its one batched read whether `urls` is set or not, and `urls` only converts it for links: with 250 links in Safari a snapshot took 2.7 ms (0.8%) longer than before without `urls`, within noise, and 10 ms (3%) longer with it. Windows makes no extra call in a tree, since a link's target is the value its cached read already holds. With `since: true` the macOS, Windows and Linux desks answer what changed since the caller's last snapshot of that window, the caller being the call's `agent_id` and the window its `id`: `diff: true`, `focused` (the node in the focused state, or null), `added` and `changed` (nodes as above, whose `ref` and `parent` index the current tree) and `removed` (the `id`, `role` and `name` of each node gone). A node is matched by its role, its name, its ancestors and its place among siblings with the same role and name; the window's own title is left out, so a retitled window changes only its root node. A node is changed when any field other than `ref` and `parent` differs, its `bounds` included unless `bounds: false`. The answer is the whole tree with `diff: false` instead when the caller has no earlier snapshot of that window, or when the diff would not be shorter. Each answer becomes the caller's new baseline; the desk keeps the baselines of a caller's last 8 windows, and 32 in all, dropping the oldest first, and drops a `gui_plan` or script run's baselines when it ends. `since` with `text` is refused. Without `since` nothing is kept and nothing is compared; with it, a snapshot costs one comparison over at most 2500 nodes and the serialization of the diff beside the tree's, and holds one tree per caller and window. Every answer also carries `matches`, how many windows share the title, when `window` names more than one, the active one being read (a device gives no `matches`); `window`, the window's entry of `windows` without the `shell`, `modal` and `blocks` that the list adds on Linux; `truncated`, true when the walk stopped at the node limit, or, on macOS, when its read ran out of time or an element did not answer within 500 ms, which leaves out what is below it, or, on Linux, when a node's children could not be read, while elements the depth limit leaves out do not set it; `ms`, the time the snapshot took; and `phases`, the time of its parts: `frames` for picking the window, then `walk` and `menubar` on macOS, `items`, `walk` and `menus` on Windows, and `items`, `parse`, `live` and `extras` on Linux. The times are in milliseconds and differ from call to call, so leave `ms` and the values of `phases` out when two answers are compared. An Android device ignores `since` and answers the whole tree without `diff` and without `phases`, and answers `truncated: true` with the window node alone when the app gave its window no tree, as a busy app can |

## Computer calls

A vision agent drives the screen with these, by screenshot pixels and element indexes rather than desk ids. The desk answers them on Linux X11, macOS and Windows, and an Android device answers its own `computer_state`, `computer_act`, `computer_end` and `look`, where `computer_act` takes one action per call: `tap` or `click`, `double_tap` or `double_click`, `long_press`, `swipe` or `drag`, `scroll`, `type`, `key`, `launch_app` and `wait`. On macOS and Windows the screenshots and the settle come from cua-driver's captures, keys and typing go to the frontmost window, input at a screen point goes in the foreground since it moves the pointer, no modal lines appear, a left click on a text field asks cua-driver for a hit-checked `verify_hit` click, which the bundled cua-driver delivers: the driver brings the field's window to the front and clicks the field's centre only when the element on top there is that same field or inside it, so the keys that follow reach the field; when the driver refuses, the field gets its press action and, if the field refuses that, the driver's refusal, never a click at a point; on Windows, where a field's press action is a click posted to its window at the field's centre, the driver's refusal stays the result, with nothing sent; a left click, double click or triple click on another element whose macOS app refuses its press action gets one `verify_hit` click, and when the driver refuses that too the result carries both errors, never a click at a point; a press that fails any other way is not repeated. With an app allowlist they are refused, since they see and click the whole screen. `session`, a string (a number counts as its digits; any other type is refused with nothing sent), names the driver session whose elements and screenshot scale a call uses. Without it, a call uses the caller's own default session, named after its `agent_id`; a `script_run` or `gui_plan` run's default session ends with the run; calls with neither `agent_id` nor `session` share one default session, and `shuttle desk` calls, which send `agent_id` `desk`, share theirs. `look` and `title_at` take no default session: a `look` without `session` takes a one-shot session of its own. A call on an ended session starts it again under the same name, so its next element action needs a new `computer_state`; other callers' default sessions are left as they are.

## Runs

`script_run` (`code` or an absolute `script` path, which the MCP server resolves against its own working directory, the agent's on stdio; over `--http` a `script` names a file on shuttle's machine, so a remote agent passes `code`; `params`, default `{}`; `timeout_s` up to 110, default 90) runs one module on the bundled Node, with the desk API as the global `desk`, and answers `{result, logs, stderr, exit_code?, duration_ms, usage?, error?: {kind, message}}` (no `exit_code` after a timeout or a stop; `usage` is `{<model>: {calls, input_tokens, output_tokens, cached_tokens}}` of the model calls the run made through the desk API, kept after each call so a run that times out or is stopped still reports them, and absent when it made none): `kind` is `import` (the module or the desk API failed to load), `no_main` (the module exports no `main` function), `exception` (`main` threw; `message` is the stack), `timeout`, `stopped` (the user stopped shuttle), `result_too_large` (`main` returned over 16 MiB of JSON; the run finished and the result is dropped) or `exit` (Node exited without saying why). A report that carries `error` answers with `is_error: true` and the whole report as its text, so an MCP client sees the run fail with its logs. `gui_plan` runs the runtime's plan executor with its arguments and answers the plan's result, or an error when the plan reports one. Two arguments serve an agent host instead of a plan: `{locate: {target, press?}}` resolves `target` in the focused window's tree and answers `{found, how, role, name, bounds, shown, shift, window, pid, ms}`, with `via` when it pressed and `unverified` when that press was sent but not confirmed, or `{found: false, why, window, ms}` when nothing matches (no `window` when no window is focused), pressing the element with `press: true`, and either carries `served` when a model ran; `{reindex: true}` rebuilds the flows' `INDEX` and commits the flows git. `DESK_FULL_CHECK=off` in the daemon's environment, which a run inherits, drops the last stage of a grounded click's check, the whole screen with a ring at the point. A `gui_plan` that a timeout or a stop ends answers an error that ends with `; what it left:` and the plan's `{ok: false, done, trace, escalate, unverified?, caveats?, usage?}`, so the caller sees which steps ran and which of them were not confirmed. `done` counts the steps that ran; `escalate.step` names the step to check before continuing. Both run with `SHUTTLE_SOCKET` naming the daemon's endpoint, `SHUTTLE_AGENT` naming the run (the runtime sends it as `agent_id`, so the run's own desk actions pass while it owns the desk), for `gui_plan` also `SHUTTLE_CALLER`, the calling session's agent id, which keys the chain record, and without the model key variables (`OPENROUTER_API_KEY` and the configured `api_key_env`); logs and stderr keep their first 32 KiB. A timeout, a stop or a cancelled call ends the run on macOS and Linux with SIGTERM to its process group, so the script can clean up (release the keys it holds, close what it opened), and with SIGKILL to whatever is left of the group 2 s later; a client that closes the connection during that grace gets the group KILLed at once; on Linux the apps the desk moved into systemd scopes of their own are spared. The report then comes at most about 2.5 s after the timeout (the 2 s grace, then up to 0.5 s for its output pipes; a process stuck in the kernel delays the report until it leaves it), with `kind` `timeout` or `stopped` and the logs kept. On Windows the run's Job object ends at once with every process in it, since Windows has no SIGTERM. A run that ends by itself leaves the processes it started. A run whose daemon dies without ending it (SIGKILL, a crash) notices within a second on macOS and Linux, sends SIGTERM to its process group and exits. While `config.toml` fails to load, every call except `safety_stop` and `safety_resume` answers with its error, since the key variable and the safety controls are in it. `safety_stop` and `safety_resume` (no arguments, what `shuttle stop` and `resume` send) halt every call, ending the run and the desk and model calls in flight, and lift the halt; no MCP tool and no runtime call sends them, and the daemon answers them only to a peer that runs as its own user.

### Verify steps

A `verify` step reads the plan window's tree once and stops the plan when no element matches its target, or when the element fails its `value`, `on` or `enabled`. With `timeout_ms` (a whole number of milliseconds, from 1 to the run's `timeout_s`, which is 90 s by default and 110 s at most) it reads the tree again every 200 ms until the element resolves and holds them, or until `timeout_ms` passes or the run is 3 s from its own timeout, and then stops with the reason of its last read; a model picks the element only on the last read, so each earlier read costs one snapshot, and a verify that passes without a model on a later read, after a read whose complete snapshot did not hold the element, confirms the step before it, as a `value`, `on` or `enabled` verify does, and a `gone` verify does only when an earlier read showed the element. With `gone: true` it passes when a complete snapshot contains no shown element of that name, with or without bounds, matched without a model on the first 80 characters of the name, so a shown element that shares them counts as still there, and with `timeout_ms` it waits for that; a `gone` step that still finds the element stops with `verify: "<name>" is still there`, and one whose snapshot was truncated without the element stops with `verify: snapshot is truncated; cannot confirm "<name>" is gone`. A step with `gone` and `value`, `on` or `enabled`, and a verify step's `timeout_ms` outside that range, are refused before anything runs.

### Recorded steps

A `gui_plan` step can carry fields that a recording writes. `after` names the window the recording saw in front after the step: the step then waits for a window of that title to come to the front by itself (`timeout_ms`, default 5 s), or, under background input, to open in the plan's app; unlike a `wait` step under foreground input, it never focuses a background match, and when the window does not come the plan stops with an error (`is_error: true`, the reason in `error`), since the replay no longer follows the recording. `recorded`, on a `click` step, is `{text, crop?, scale?, offset?, at?, size?, root?}`: the target the recording clicked as text, a base64 PNG of the area around the point at `scale` pixels per desk unit (default 1), the point's offset in desk units from the crop's centre (default none; a crop cut at the window's edge is not centred on its point), the point relative to its window's top-left corner and that window's size, and `root` when the point hit the window or document itself rather than an element.

A `click` step can carry `button` (`right`, `middle`), `count` (2 for a double click) and `mods` (modifier keys held): it then clicks the element's centre, or the point a fallback found, with them, instead of pressing the element. In the foreground, and under `auto` once the window is fronted, it first hit-tests the centre as a click found on the screen does, and stops with "the centre of … is on …, so the click was not sent" when the hit lands under another window or in a window the plan window does not own; a menu entry is not checked. With background input it clicks into the plan's window by its own image, so a window on top of it does not take the click; where windows have no bounds (Windows, Linux) it fronts the window under `auto` input and stops the plan otherwise.

On an Android device, a `type` step whose `desk type` answers `typed: false` stops with `<text> did not show in the focused field`, which for a text of several lines adds that all its lines and the Returns between them were sent, and one answering `typed: null`, as for a web view, a field that changes what is typed, or a first line pasted where no field reports the input focus, carries a caveat unless it is a password. A `type` step can carry `focus`, the element the recording typed into, `{role, name, frame?, secure?}` as a snapshot names it, with the role of its window or sheet, and `secure` for a password field, which then must show the `protected` state; `{secure: true}` alone takes any focused password field: before typing, the step reads the focused element of the front window, re-reads it every 100 ms for up to 1 s until it matches, and stops the plan with an error when it is still another element or none can be read, since the text would go elsewhere. `focus: "unverified"`, which a draft writes where the recording itself read no focus (an app without accessibility), types without the check. A `type` or `set` step with `secret: true` holds a password: it is never quoted back, logged or saved as text. A `set` into a field with the `protected` state is treated as secret without the flag, is confirmed by mask characters of the value's length, and ends with a caveat where the field reads back nothing. A `type` is treated as secret without the flag when the desk's `type` reply carries `protected: true` or its error ends with ` (into a password field)`, when the step's own read shows a focused `protected` field, or under background input when an earlier step of the plan clicked, pressed or set that `protected` field, with only `wait`, `expect` or `verify` steps between. Under background input on Windows such a password, like that of a `secret: true` step into a field that reads back no value, is sent but not checked: the step stays unconfirmed with the note that the password was sent and not confirmed, and the plan ends not ok unless a later `expect`, `verify` or `wait`, or the step's `after`, reads its effect. A `type` step with `secret: true` is a password that none of these sees ([config.md](config.md#saved-flows) lists the cases), or one without a password field to point `focus` at, such as a terminal's `read -s`, `sudo` or `ssh` prompt; it holds the password line alone, so the command that asks for it goes in its own step. Like a step with `focus: {secure: true}`, a stop names it "the password" instead of quoting the text, its unconfirmed note in a stop, `escalate` or `unverified` is the fixed "unverifiable: the password was sent and the target did not confirm it; do not type it again", with " (terminal emulator)" before the semicolon when the driver's note names one, in place of the driver's note, which can give the password's length or keys, the step in `escalate` says "the password" in place of literal text and leaves out its `intent` and the window outline, the auto foreground retype never sends it, and a saved chain or flow keeps it as a parameter rather than the text, without its `intent`. Into a terminal window on another Space on macOS, which the desk cannot read, a background terminal line the driver did not confirm, a password line included, goes in with no read-back and its step stays unconfirmed: a Return of that step or of the next one submits it once, and the plan ends with "sent but not confirmed" unless a later step reads its effect. Under foreground input a step whose password line ends in a line break reads the window back after the password and stops before its Return when the password shows there; a drafted password-field step has no line break, so it is typed alone and any Return is the recording's next step, while a drafted terminal secret step ends in the Return the recorder could not see; a window whose text cannot be read gets its Return unchecked. Under background input on macOS, where the desk reports the target as a terminal, a terminal that shows the password, or changes while it is typed without showing it, stops the step the same way; a password line whose Return the terminal answers by changing its text counts as landed, so the plan does not report it unconfirmed; landed means the terminal took the line, not that the password was right, and a password that shows only after the Return stops the step with "the password showed … after its Return was sent", which also asks to clear it before any screenshot. A stop before the Return says "the password showed" or "changed while the password was typed", so the shell never runs that password; a password that showed is then erased with one Backspace per typed character, sent one at a time and only while the plan's window is still in front under foreground input, and in one `key` call with `repeat` under background input, and read back; the stop says "and it was erased" only when every element reads as it did when the password showed, less the password, read again for up to 1 s while a readable window does not yet, "it could not be erased: clear it by hand" when anything is left, another window came to the front, or Backspace could not be sent, and "Backspace was sent over it, unchecked" when there was no earlier read or the window could not be read back; a stop after the Return comes when the shell may already have run it. Where the desk's reply names no terminal, as for every Windows background type and for a macOS field that is not a terminal, a background secret line is read back before its Return too, and a password that shows there stops the step with "the password showed", or after the Return with "the password showed … after its Return was sent"; this path has no "changed while the password was typed" stop, and a window whose text cannot be read gets its Return unchecked here too. On Windows, a focused password field that exposes no value at all, as a text box with a password character does whether it holds text or not, leaves the step unconfirmed instead of stopping it with "did not show" when no other field of the window changed: the plan goes on, and the next step confirms it when it is an `expect`, a `verify` that checks a value, state or enabled or one that waited, or a `wait` that saw a new window, or the plan ends with the step sent but not confirmed. In a window with no text field, such as Windows Terminal, the read-back reads the text element that has the keyboard focus; on Windows 11 25H2, Windows Terminal behind another window dropped every background key, the Return included, so background `key` and `type` refuse it before sending anything while another window is in front and no element of it holds the keyboard focus (with the focus it takes them), and the step stops there, or under `auto` input runs in the foreground.

When the accessibility tree has no match for such a click, the step tries, in this order:

1. the crop, found on a screenshot with a normalized cross-correlation of at least 0.8, when the step's target is the recorded text;
2. grounding the target, which may land on the window or document itself when `root` is set. On a target with no accessibility element, such as a button drawn on a canvas, grounding can click a control that looks like the target, or one it takes for a target that is not there; the step's `after` stops the plan then, but the click has happened;
3. the recorded point in the window, when the step's target is the recorded text and the window has the recorded size, within 2 desk units (macOS, where windows have `bounds`).

A target that a parameter changed skips the crop and the point, since both show the recorded target. Each point must pass the hit test of a grounded click: inside the plan's window or a window it owns, under no other window. The trace names the one that clicked in `how`: `crop`, `ground` or `point`. A click without `recorded` grounds as before and refuses a point on a window or document root.

When a recorded check stops the plan (an `after` window that does not come, a `focus` elsewhere, a `web` page that differs, or a recorded click whose crop, grounding and point all miss), the result carries `error` and `stopped: {step, intent, reason, remaining}`: the step's index, its `intent` (null when the step has none), the reason, and the steps from that one on, without their `recorded` crops and fingerprints, so an agent can do the rest of the task itself. Other stops carry no `stopped`. On Linux a result carries `caveats: [{step, note}]` for the steps whose only proof is an accessibility action's reply and that the next step did not read back.

### Web steps

On macOS a step can name the web page it acts on, for a page in Chrome or another Chromium browser, or in Safari:

- An `app` step with `url` opens that address in the app (`{app: "Google Chrome", url: "https://example.com/form"}`, by `desk launch` with the address as its argument) and waits up to 10 s for a window of the app to show it; that window becomes the plan's window.
- A `click`, `check`, `set`, `verify`, `expect`, `menu` or `type` step with `web: {url, id?}` first reads the address of the plan window's page and stops the plan with an error when its origin and path differ from `url`; a query, a fragment and a trailing slash do not count. It waits up to 3 s for a navigation to finish, or for a page to show at all, first, so a redirect to another path stops the plan before anything is clicked. `id` is the DOM id of the element: a click takes the element that has it over another of the same name, and keeps the name match where no element has it, since some pages make new ids on each load. A `type` step's `focus` can carry `id` too, and then the focused field must have that DOM id.
- Chrome builds the accessibility tree of its pages only for an assistive app that asks. When a web step finds no page in the window, the plan holds the tree on with `desk web`, and the daemon turns it off again, where it was off, when the plan ends in any way and nothing else holds it.
- The first input in a browser the recording saw start can come before its page tree is built: that click then has no `web`, and replays as a click with no page check.

Values in `url` and `web.url` take `{{name}}` parameters as other step text does. On Linux and Windows the desk reads no page address or DOM id: a web step there stops at the address check, so a recorded web flow replays on macOS only.

## Recordings

`record_start` (`apps`, optional app names as `windows` lists them, `app` or `bundle`) starts recording the user's input on macOS and answers `{"ok": true, "id"}`, with a `note` when secure input is on as it starts and the focus is not in a password field, as when an app that is not in front holds it, since macOS then hides every key until it ends (the user's own password field gets no note: it records a `password` event); it fails while a recording runs, on other OSes, and while macOS refuses the event tap. The daemon answers the three recording calls only to a peer that runs as its own user. `record_note` (`text`) adds a note at the current point of the running recording. `record_stop` (`params`, optional parameter names with the values the user typed or clicked for them) ends the running recording, or takes the last one that ended, however it ended, and answers its draft (below). The recording itself stays in its file, `{id, started_ms, stopped_ms, apps, events}`, where each event has `t` (ms since the start) and `kind`:

- `click`: `x`, `y` (desk coordinates), `button`, `count`, `mods`, `app`, `late` (true when the crop had to be taken after the click), `element` (`role`, `name`, `description` as a snapshot names them), `path` (the ancestors up to the window, innermost first), `root` (the point hit no element but a window or document), `window` (`title`, `bounds`), and `crop` (a base64 PNG of the window around the point, from that window's own capture, cut at its edges; none while a sheet shows on the window, since the capture by its title then shows the sheet) at `crop_scale` pixels per desk unit with `crop_offset`, the point's offset in desk units from the crop's centre, and `secret` when the element is a password field, and `web` (`url`, the address of the page, the top page for a click in a frame, and `id`, the element's DOM id when it has one) for a click in a web page; a click on the text of a link or button names the link or button;
- `key`: `code`, `text`, `mods`, `app`, and on the first key of a run of typing `focus`, the element it went to (`role`, `name` as a snapshot names it, `frame`, the role of its window or sheet, `window`, the title of its window, `secure: true` for a password field, and `url` and `id`, the page address and DOM id, for a field in a web page) or null when none could be read; or `secret: true` with no text for a key typed into a password field;
- `password`: `app`, the app of the focused element, and `focus`, when macOS turned on secure input, after which the keys reach no listener. `focus` has `secure: true` only when the element is a password field; at a terminal's password prompt it is the terminal's text area. In an app the recording leaves out, or one it cannot name, the event is `skipped`;
- `after`: `window`, `role`, `app` of a new window in front once the input settled for 0.7 s, or when the recording stops, as a page that loads after the last click does;
- `note`: `text`;
- `skipped`: input in an app the recording leaves out, with no detail.

The draft is `{id, apps, params, steps, notes, gaps, recording}`: `steps` is a `gui_plan` plan with an `intent` on each step, which `gui_plan` runs as given or saves as a flow with `save`; `recording` is the file's path. The runtime builds it from the events:

- The first click's app becomes an `app` step, at the first click's window when it names one, or at the window of the first key's `focus` when the recording starts with typing. A click or a key that goes to another app, or a click in another window of the app than the one in front, first becomes an `app` step there, at that window when the click names one; a window an `after` event brought to the front needs none.
- A click on a menu-bar entry and the click on the menu item after it become one `menu` step, such as `File > New`, with the submenus the item's recorded path names, such as `File > Export > PDF`.
- Other clicks become `click` steps on the element's name, with its `role` for a named button, check box, radio button, tab, link, switch, toggle button or menu item. A right click, a double click (one step, not two) and a click with modifiers keep `button`, `count` and `mods`. A click on no named element, or on a window or document, takes a name the `ask` model gives its crop with the point ringed and the element's role, such as `the Green button`; the model can name the wrong one of two similar controls, so check these names in the draft. Captions run four at a time within 75 s of the draft's start: a click whose caption would start later, is not answered by then, or fails, is named by its role and point, such as `the button at 320, 100`, and the first click of a double click gets no caption when its step merges into the second, which it does unless a step comes between them, such as a switch to the window the first click opened. Each click carries `recorded` ([Recorded steps](#recorded-steps)): its target text, crop, scale and offset, its point relative to its window and that window's size, and `root` for a click on a window or document.
- Keys with no modifier other than Shift become one `type` step per run, and other keys `key` steps with all their modifiers, a key held with Command or Control named by its own key in the keyboard layout (cmd+alt+c records `c`), Shift too, such as `cmd+w`, `shift+tab` or `return`. A click into a password field, a `password` event, and keys a password field took become one password `type` step, since a recording holds no password: `password` (then `password_2` and so on) is in `params` as `{"secret": true}`, and the replay needs its value. macOS hides every key typed into a password field from the recorder, including the Return or Escape that ends it, so a recorded login needs its submit step added by hand.
- Each `type` step carries the `focus` its first key recorded, so the replay stops where the focus is elsewhere; where the recording read no focus it carries `focus: "unverified"`. A password step is never unverified. Where the recording read a password field, its `focus` has `secure: true`, and it is `{secure: true}` alone where the recording read no field, so the replay types it only into a password field. Where the password went to an element that is not a password field, such as a terminal's prompt, the step is `{type: "{{password}}\n", secret: true, focus: {role, name, frame}}`: the `focus` names that element without `secure`, so the replay types the password only where that element has the focus and stops elsewhere. Its text ends in the Return that a terminal prompt takes the password with, which the recorder does not see either.
- An `after` event of role `window` with a title not seen before in the recording becomes the `after` of the step before it, unless that step is an `app` step.
- Input in a web page ([Web steps](#web-steps)) carries `web: {url, id?}` on its step: a click with the page address and the element's DOM id, a typed run with the page address and `id` in its `focus`. The first step into a web page, at the start or on a switch, is `{app, url}`, which opens the address, in place of `{app, title}`.
- Each value `params` names, wherever it appears in a typed run, a click target, an `after` title or a page address, becomes `{{name}}`, and `params` in the draft holds `{"example": value}` for it. Other typed text stays literal.
- `notes` holds each note with the index of the step it came before, and `gaps` the step indexes where the recording skipped input.

[safety.md](safety.md#recording) says what a recording holds and leaves out.

## Plugins

A plugin adds one tool that runs scripts with `script_run`'s contract and its own program in place of Node. This section is the schema's source of truth.

- **Where.** One `*.json` file per tool in the plugin directory: `tools.d` next to `config.toml`, or the directory `[tools] plugins` names ([config.md](config.md)). The daemon reads it when it starts and the MCP server when an agent starts it, in file-name order.
- **Spec.** `{"name": string, "description": string, "bin": string, "resources"?: [{"uri": string, "path": string, "mime": string, "description": string}]}`, and no other field.
  - `name` matches `^[a-z][a-z0-9_]*_run$` and is no built-in tool (`gui_plan`, `script_run`, `desk`, `screenshot`, `status`, `record_start`, `record_note`, `record_stop`) and no earlier file's name.
  - `description` is at most 2048 characters.
  - `bin` and each resource `path` are absolute.
  - Each resource `uri` appears once in the file and in no earlier file.
  - A file that breaks any rule, does not parse or holds an unknown field is skipped whole, with one log line naming the file and the reason; no part of it loads.
- **Calls.** The tool takes `script_run`'s arguments and answers its report. The daemon runs `bin` exactly as it runs Node for `script_run`: the runtime's entry module as the one argument, which `bin` runs in its own process (exec), since an entry left as a child of a wrapper does not see a daemon that died, the same `SHUTTLE_SOCKET`, `SHUTTLE_SCRIPT`, `SHUTTLE_RUN`, `SHUTTLE_FLOWS`, `SHUTTLE_AGENT`, `SHUTTLE_INPUT` and `SHUTTLE_DESK` (`android` when the desk drives an Android device, else `native`), the result, error and usage files in `SHUTTLE_RUN`, the same timeout, stop and output caps, and no model key variables. A desk call the program makes on `SHUTTLE_SOCKET` goes through the same app allowlist, confirm mode and stop as every other desk call.
- **Switch.** `script_run = false` turns the plugins off with it: the MCP server lists none and answers one as an unknown tool, and a desk-wire call answers as `script_run` does.
- **MCP.** `tools/list` lists each plugin after the built-in tools, with `script_run`'s input schema. The resources of every plugin are listed by `resources/list` (`uri`, the file name as `name`, `mime` as `mimeType`, `description`) and served as text by `resources/read`; `initialize` names the `resources` capability when there is one.

A neutral example, `tools.d/demo.json`:

```json
{"name": "demo_run", "description": "Run a demo script.", "bin": "/usr/local/bin/demo-runner", "resources": [{"uri": "demo://GUIDE.md", "path": "/usr/local/share/demo/GUIDE.md", "mime": "text/markdown", "description": "The demo guide"}]}
```

## Service plugins

A service plugin is a long-lived program that serves its own tools on the desk wire. The daemon runs it as its child and hands it the connection of every call of one of its tools. This section is the schema's source of truth.

- **Where.** A `*.json` file in the plugin directory with a `service` key is a service; any other file is a plugin of [Plugins](#plugins). The same file-name order applies, and the daemon and the MCP server read the directory as for plugins.
- **Spec.** `{"service": string, "bin": string, "args"?: [string], "tools": [{"name": string, "description": string, "input_schema": object, "mcp"?: bool}]}`, and no other field, in the file or in a tool.
  - `service` matches `^[a-z][a-z0-9_]*$`, is at most 32 characters and is no earlier file's service.
  - `bin` is absolute; `args` defaults to none.
  - `tools` holds at least one tool. Each `name` matches `^[a-z][a-z0-9_]*$` and is at most 64 characters. It is no built-in tool (`gui_plan`, `script_run`, `desk`, `screenshot`, `status`, `record_start`, `record_note`, `record_stop`), starts with none of `desk_`, `model_` and `safety_`, does not end in `_run`, which plugins take, and is no other tool of this file or an earlier service.
  - `description` is at most 2048 characters; `input_schema` is a JSON Schema whose `type` is `object`.
  - `mcp`, default `true`, lists the tool on MCP; with `false` the tool is reached on the desk wire only, which suits a tool that streams frames.
  - A file that breaks any rule is skipped whole, with one log line.
- **Process.** The daemon starts `bin` with `args` when it starts, in your home directory, in a process group of its own (on Windows, a Job object of its own), with:
  - `SHUTTLE_SERVICE_SOCKET`: on macOS and Linux the unix socket to listen on, `services/<service>.sock` beside the daemon's endpoint, in a directory of mode 0700 that only your user reaches, where the daemon removes a file left at that path before each start; a path longer than a unix socket takes (103 bytes on macOS, 107 on Linux) fails the daemon's start with an error that names the service; on Windows the named pipe to serve, the daemon's pipe name followed by `-svc-<service>` (`\\.\pipe\loomhand-shuttle-desk-<SID>-svc-files`), whose security must admit your user;
  - `SHUTTLE_SOCKET`: the daemon's endpoint, for the service's own desk calls, which pass the same app allowlist, confirm and stop as any other;
  - no model key variables (`OPENROUTER_API_KEY` and the configured `api_key_env`).
  When the service exits, the daemon kills the rest of its process group (on Linux, all but the apps the desk moved into scopes of their own) and starts it again after 1 s, doubling the wait on each exit up to 30 s; a service that ran 30 s or more starts again after 1 s. When the daemon exits, it sends the service SIGTERM, waits 3 s, then kills its group. A daemon that is killed outright cannot do this; on macOS and Linux the next daemon, before it starts a service, sends TERM to whatever still listens at that service's socket and to the process group it leads, and KILL to what is left 3 s later. Only processes of your user can listen there, since the socket's directory is yours alone. On Windows a service's exit, a stop of the daemon and the daemon's own end by any means, `taskkill /F` and logoff included, kill the service's Job object with every process in it: Windows has no SIGTERM, so a service gets no notice.
- **Calls.** The daemon reads a call's first frame. When its `tool` names a service tool, it connects to that service's socket, waiting up to 10 s while the service starts or, on Windows, while every instance of its pipe is busy, on Windows refuses a pipe served by another user as the desk's own pipe does, writes the frame exactly as it read it, and then copies bytes both ways. Nothing after the first frame is parsed, and no frame size or deadline applies. When either side closes its end, the daemon closes the other side's input and keeps passing on what the other side sends; the call ends once both sides have closed their ends, or at the first error. Windows pipes have no half-close: there the first side to close its end ends the call, and the daemon closes both connections, so a client or service that marks the end of what it sends does so with a frame of its own. A call no service listens for within 10 s answers with an error frame that names the connect error and, when the service has exited or failed to start since the daemon started, its last exit or start error; a frame the daemon cannot write to the service answers with the write error.
  - A service call takes no desk turn: it runs alongside runs and desk actions.
  - Work a service starts for a call, such as a shell command, is the service's to end when its connection closes; shuttle does not end it.
- **Stop.** `safety_stop` refuses new service calls with `stopped by the user` and closes every connection in flight, without a reply, since its client may be inside a stream of its own frames. The service keeps running, and `safety_resume` lets calls through again.
- **Switch.** Installing a service file is what turns the service on: `script_run = false` turns plugins off but leaves services running, listed and reached.
- **MCP.** `tools/list` lists each service tool with `mcp` true after the plugins, with its own `input_schema`. `tools/call` sends one frame and reads one response frame through the daemon, so a tool the MCP server lists answers one response frame.
- **Cost.** A desk call pays nothing when no service is installed. With one installed, every call that is not spliced pays a read of its `tool` before its full decode and one lookup in the service tool table. A service call pays one unix-socket connect and the copy through a 64 KiB buffer each way; a microbench (`cargo test -p shuttle --release splice_cost -- --ignored --nocapture`) measures it.

A neutral example, `tools.d/notes.json`:

```json
{"service": "notes", "bin": "/usr/local/bin/notes-service", "args": ["--serve"], "tools": [{"name": "notes_read", "description": "Read a note.", "input_schema": {"type": "object", "properties": {"title": {"type": "string"}}, "required": ["title"]}}, {"name": "notes_watch", "description": "Stream note changes.", "input_schema": {"type": "object"}, "mcp": false}]}
```

## Model calls

The daemon answers these with the models of [config.md](config.md) (`crates/models`), so a script calls a model without holding a key. Each reply carries `usage`: `{model, input_tokens, output_tokens, cached_tokens}`.

| Tool | Arguments | Result |
|---|---|---|
| `model_decide` | `state` (text, JSON, or a list of text and `{type: "image_url", image_url: {url: "data:image/png;base64,..."}}` parts), `questions` (`{key: {type: "noul" \| "choice", instructions, criteria?}}`), `image` (the state holds a screenshot: the `verify` role answers, else `decide`), `timeout_ms` (caps the configured timeout; `desk.look` passes 5000) | `answers` (`{key: {probability}}` for a yes question, `{key: {choice, confidence, probabilities}}` for a choice), `served` (`{model, build, id}`: the model name asked, and the build and generation id that answered, null when the endpoint names none) |
| `model_ask` | `prompt`, `images` (PNGs as base64) | `text` |
| `model_ground` | `png_b64`, `target`, `area` (`{left?, top?, width, height}`) | `x`, `y`; a point outside 0 to 1000 is an error, and 1000 maps onto the last pixel of `area` |

An endpoint that answers 402 Payment Required fails the call with an error that starts `model credits are used up:` and names the model, the endpoint and the reason it sent. `gui_plan` stops at that step with no retry and no fallback model call, and answers `is_error: true` with the message in `error` and `escalate.reason`; in `script_run` it is the exception a desk model call throws.

### Coordinates

Desk coordinates are the space `desk_screen` reports and `desk_click`, `desk_at`, `desk_shot` and element `bounds` use: screen pixels on Windows (the desk host is per-monitor DPI aware) and on Linux, and on macOS the main display's pixels (AX points times its backing scale), negative left of or above it. A GTK 4 app on Linux answers no screen position, so its elements carry no `bounds`, `desk_at` refuses its windows, and a press runs the element's action. A screenshot need not have that size: `desk_shot` may return a downscaled image, and a Retina capture can be 2x. `desk_click`, `desk_scroll` and `desk_drag` with `window` take pixels of the whole image `desk_shot` with that `window` returns instead: the window's own capture, 2x on a Retina display, whichever display shows it. Pixel (`px`, `py`) of a cropped shot is (`origin[0] + px`, `origin[1] + py`). A title that matches two listed windows alike (both equal to it, or both containing it) is refused there, since a shot by that title may show the other window: pass a longer title that only one window matches, give the window a title of its own, or pass desk coordinates without `window`. On an Android device they stay screen pixels.

`model_ground` takes `area`, the desk rectangle the PNG shows, and returns `x`, `y` in desk coordinates: the model answers a point from 0 to 1000 across and down the image, and the daemon maps it onto `area`, whatever the PNG's own size. Pass the rectangle the PNG was cropped from, never the PNG's width and height.
