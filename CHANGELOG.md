# Changelog

## 0.1.33 - 2026-10-30

- **MCP tools to record a demonstration and replay it.** `record_start`, `record_note` and `record_stop` start and stop a recording on macOS, as the menu-bar item does. `record_stop` answers a draft `gui_plan`: an `app` step, and one more each time the input moves to another app or window, menu clicks merged into `menu` steps, clicks with their button, count, modifiers, recorded crop and point, typed runs and keys, the window each step left in front as `after`, and each value the caller names in `params` as `{{name}}`; a password the user typed becomes a secret parameter to pass at replay, typed only into a password field. [wire.md](docs/wire.md#recordings) has the rules.
- **macOS: recordings of what you do.** Start recording from the menu-bar item (or `record_start` on the desk wire), work, and stop it: shuttle keeps each click with the element under it, read before the app handles the click, its window and a crop around it from that window's own capture as it was before the click, each key, the window that came after each action, and your notes, in a 0600 file under `~/Library/Caches/loomhand/shuttle/recordings`. Keys typed into password fields, input in password managers, Keychain Access, Passwords and System Settings, and shuttle's own menu are left out. [safety.md](docs/safety.md#recording) has what a recording holds.
- **A plan no longer passes behind an alert shown on a macOS sheet.** A sheet shown on another sheet, such as TextEdit's "already exists. Do you want to replace it?" over its Save sheet, is now a window of its own in `windows` (a `dialog` whose `owner` is the sheet below it) and takes the app's focus there. Before, no window of the app was active while it showed, so a plan that saved under a taken name ended `ok: true` with the alert still open.
- **Recorded steps.** A `gui_plan` step takes `after`, the window a recording saw after it, and stops the plan with an error when it does not come; a `click` takes `recorded`, which lets a click the accessibility tree cannot place try the recorded crop, then grounding (also on a window or document root the recording clicked), then the recorded point in a window of the recorded size. The trace names the one that clicked. A `type` step takes `focus`, the element the recording typed into, and stops the plan with an error when the focus is elsewhere. [wire.md](docs/wire.md#recorded-steps) has the fields.
- **macOS windows carry their bounds.** `desk windows` lists each window's `[x, y, w, h]` in desk coordinates.
- **`computer_state` element lines leave out U+FFFC.** Accessibility text holds U+FFFC where an embedded object sits, and an element line showed it, as in `panel "￼￼￼￼"`. The lines now leave it out of names and values; the element kept for later actions keeps the driver's name.
- **A desktop click reply names its point in screenshot pixels.** `computer_act`'s reply to a click at x,y read `Sent screen-absolute click at (…)` on Linux and `Sent screen-absolute click at desktop-pixel (…) → screen-point (…)` on macOS, though x,y are read in the caller's screenshot and the reply's point is mapped back to it. It now reads `Sent click at screenshot point (x,y)` on both, with the driver's scope note after it.

## 0.1.32 - 2026-10-30

- **macOS: a window is found by its whole title.** Input that names a window by the title `desk_windows` lists now finds it where cua-driver lists a shorter title. Chrome gives the window server a title elided in the middle and without its app and profile suffix, so a key, type or `gui_plan` step naming a long Chrome window by its full title was refused with "no window", and the error listed the elided titles. Titles now come from accessibility, matched to the driver's windows by window number, in the error too. It costs nothing: the accessibility window list is already read whenever a title is not unique in the driver's list.
- **`launch` takes command-line arguments.** `desk launch` with `args` passes them to the app, so `{"app": "Google Chrome", "args": ["--profile-directory=Profile 1", "--new-window", "https://example.com"]}` opens the URL in a new window of that Chrome profile. On macOS the arguments start a new instance, which Chrome hands to its running instance.

## 0.1.31 - 2026-10-30

- **Input that names an app goes to that app or nowhere.** `key`, `type`, `click`, `scroll` and `drag` take `app`, the app name a window lists, and send to that app's window as with its `pid`; when the app has no window, the call fails and sends nothing. Before, the desk ignored `app`, so a call naming an app that had just been launched in the background, with no window yet, went to no target; with `input = "auto"` it then ran in the foreground and the keys reached whichever app was in front.
- **Auto input never takes the foreground for an action with no window.** An action that background input refused for want of a target window stays refused instead of running in the foreground into the front app.

## 0.1.30 - 2026-10-29

- **Bundled:** cua-driver v0.38.0-loomhand.10 (was v0.38.0-loomhand.9).
  - macOS: background typing into a window with no focused accessibility element no longer makes that window lose and regain key before the first key ([loomhand/cua#13](https://github.com/loomhand/cua/pull/13)). WeChat is such a window, and so is any Qt app drawn without an accessibility tree. The driver sent a defocus and a focus record for the window it was about to make key, and a Qt app that resets its focus on focus-in sent the text meant for its search field into the chat input. A chat-like Qt fixture with that reset now takes the text in its search field 3/3, where it took it in the chat input 4/4, and a LibreOffice Writer that was never active still takes background text, 2/2.
  - macOS: a desktop capture wakes a display that is off, or refuses with `display_asleep` ([loomhand/cua#12](https://github.com/loomhand/cua/pull/12)).
  - macOS: background `type_text` and `press_key` take `locked_input`, which sends the keys while the screen is locked ([loomhand/cua#14](https://github.com/loomhand/cua/pull/14)).
- **macOS: background typing and single keys can work under a locked screen.** `[desk] locked_input = true`, off by default, sends a background `type` or single-key `key` while the screen is locked instead of refusing; the result is unverified, and the keys go to the app's key window as it was before the lock, since the lock hides every window from accessibility. Key combinations, clicks and every other action still refuse. An older cua-driver refuses the setting before anything is sent. [config.md](docs/config.md#desk-input) lists the caveats.
- **A model endpoint out of credit says so.** When the model endpoint answers 402 Payment Required, `model_decide`, `model_ask` and `model_ground` fail with `model credits are used up: <model> at <endpoint> returned 402 Payment Required[: <reason>]; add credit or upgrade the plan, then try again`, and a `gui_plan` step that gets it stops the plan as a tool error with that message. Before, the error read `<model> at <endpoint> returned 402 Payment Required: <body>`, and in a plan a 402 on a screenshot pick or on the check of a grounded point fell back to more model calls and could end as a generic "no element matches".
- **The desk tool says where background typing in WeChat goes wrong.** Its description and safety.md note that in a macOS Qt app with no accessibility focus, such as WeChat, background typing into a search field can land in another field, and to reach a chat by scrolling its list or with foreground input.
- **A run that dies without reporting its error names its stderr.** When Node exits nonzero without writing its error (an uncaught exception outside `main`, or a runtime that cannot start or write its run directory), the `gui_plan` and `script_run` error now ends with the last 2 KiB of the run's stderr. Before, it said only `node exited with exit status: 1`.
- **A desk call waits out a cua-driver restart.** After cua-driver dies, the daemon starts it again; a desk call made meanwhile now waits up to 10 seconds for the restarted driver instead of failing at once with `Connection refused`.

## 0.1.28 - 2026-10-28

- **Bundled:** cua-driver v0.38.0-loomhand.8 (was v0.38.0-loomhand.7).
  - macOS: a background pixel click on a text input whose accessibility press leaves it unfocused now gives it the keyboard focus, as a real click does ([loomhand/cua#11](https://github.com/loomhand/cua/pull/11)). A Qt line edit takes the press and does nothing, so a click on a Qt search field left the focus in the chat input, and the text typed next went there. On a Qt chat window in the background, a click on its search field followed by `type` now puts the text in the search field, 3/3 on the main display and 3/3 on a second display; AppKit fields, which mostly decline the press, take the routed click as before.
- **macOS: background typing refuses a field the click did not focus.** A background `type` reads the app's focused element first, names it in `focused`, and refuses, sending nothing, when the last background click into the same window left a text field focused that does not contain the click point. Before, a click on a Qt search field that left the focus in the chat input sent the typed text into the chat input, and the driver even confirmed it there. A background `click` result names the focused element afterwards, with `at_click` for a text field. When accessibility shows no focused text field in the app, as in WeChat, a `type` after a background click into that window refuses until the call passes `focus: "unverified"`, and then its `unverified` says the focus was not verified. The check costs one accessibility read per background click and type.
- **A `delivery_mode` the desk does not use is refused.** A desk action that passes `delivery_mode` other than the mode `[desk] input` sends input in is refused before anything is sent. Before, shuttle ignored the argument, so a `click` asking for `"foreground"` on a background desk went in the background and reported success.
- **A plan that continues a stopped flow replay saves the fix into the flow.** When a replayed flow stops at a step, a plan run next from the window it left continues it, and when that plan passes, the flow is saved as its steps before the one that stopped followed by the plan's steps. Before, a flow run dropped the steps of the last plans, so the continuation was saved nowhere and the flow failed at the same step on its next replay. The stop for a field that already holds text now says to continue the flow rather than replay it.
- **A run reports the model calls it made.** A `script_run` or plugin run's report carries `usage`, by model, for the `ask`, `ground` and `decide` calls it made through the desk API, as `gui_plan` reports its own. The runtime keeps the tally in the run directory after each call, so a run that times out or is stopped reports them too. Before, these calls were metered nowhere a caller could read, so a box agent's turn usage left them out.

## 0.1.27 - 2026-10-28

- **Linux: desk reads GTK 4 apps' controls as usable.** A node is now disabled only when it is neither enabled nor sensitive. GTK 4 marks a usable widget sensitive and never enabled, so before, desk called every control of a GTK 4 app disabled and `gui_plan` refused to click it, as with the Save button of Chrome's GTK 4 "Save File" dialog. GTK 3, Chromium, Qt, Firefox and LibreOffice set both states together, so their greyed-out controls still read as disabled: Mousepad's Save As refuses Save while the name is empty.
- **Linux: a GTK 4 app gives no screen position.** GTK 4 answers every screen point and extent with the origin, so for an app whose toolkit is GTK 4, elements carry no `bounds`, `desk_at` refuses its windows, and a press runs the element's action. The toolkit is read once per app; a failed read is retried on the next call.

## 0.1.26 - 2026-10-27

- **Bundled:** cua-driver v0.38.0-loomhand.7 (was v0.38.0-loomhand.6).
  - Linux: a session whose GNOME Shell owns its bus name counts as GNOME even when the driver's environment names no desktop (no `XDG_CURRENT_DESKTOP`, `XDG_SESSION_DESKTOP` or `DESKTOP_SESSION`, as in a service started on OSWorld's Ubuntu 22.04 guests), so the driver advertises only `IsEnabled` and no longer sets `ScreenReaderEnabled` ([loomhand/cua#10](https://github.com/loomhand/cua/pull/10)). The cost is one round trip per app.
- **A model error names the endpoint.** A model call that fails to connect or times out now names the URL it requested, as `anthropic/claude-sonnet-5 request to http://127.0.0.1:9/v1/chat/completions: ...`, and one that gets an error status names the URL that answered, after any redirect, as `anthropic/claude-sonnet-5 at https://gw.example/v1/chat/completions returned 502 Bad Gateway: ...`, so a misrouted `base_url` shows in the error. The URL is printed without credentials, query or fragment, so a key in it stays out.

## 0.1.21 - 2026-10-26

- **Bundled:** cua-driver v0.38.0-loomhand.4 (was v0.38.0-loomhand.2).
  - macOS `list_windows` without `on_screen_only` ranks `z_index` by the live front-to-back order and gives off-screen windows `null` ([trycua/cua#5395](https://github.com/trycua/cua/pull/5395)), so the highest `z_index` is the frontmost window. Before, a TextEdit window covered by Safari ranked above it, and an off-screen window could hold the highest value. The order comes from a list of window ids, read only where `z_index` is read, so clicks and window reads cost what they did.
  - macOS: a pixel action reuses the capture scale that a read of the same window at the same bounds and display layout already proved, instead of capturing the window again: a background click right after a window read takes about 0.62 s in place of 0.66 s on a test VM.
  - The net-zero key edit after a background accessibility write into a single-line native field, added in v0.38.0-loomhand.2, is removed. WeChat's search box turned out not to be in its accessibility tree, and no native field needed the edit, which cost two keys and 150 ms per write.

- **macOS: a press on a button in the front window runs its press action.** `press` on a button, check box, switch or link in the front window runs the element's AX press action instead of clicking its centre: a button on a Safari page takes about 4 ms in place of 0.2 s, a native button about 0.1 s in place of 0.2 s, and a press on a web page still counts as user activation (a `window.open` popup and a clipboard write both run). A press the app does not answer within 500 ms, as a button that opens a modal alert, now counts as done, in the background too: before, the background press then also clicked the button, and its result said `click`. Such a button takes about 0.5 s in place of 0.2 s in the foreground. An element in a window behind takes a click as before, which brings its window to the front.
- **macOS: faster foreground clicks.** A foreground click at a point now reaches its window as a real click: shuttle brings the window to the front, as before, and asks cua-driver for foreground delivery, which moves the pointer to the point and clicks there. Before, cua-driver took the click for background input, made the window key without raising it and posted a routed event stream, and where an accessibility hit test at the point found an element it ran that element's press action instead of clicking, which System Settings' sidebar ignored (0 of 5 sidebar clicks changed the pane; now 5 of 5). The first click in a window reads only its pixels for the scale, not its accessibility tree, and with foreground input the driver's window watch after each action waits 50 ms in place of 300. When another app's window covers the point on any window level, as a floating panel can, the click goes to the window under it in the background, as before, and its result says which app covers the point in `unverified`, since the real pointer would hit that app; so does a click whose point the accessibility hit test cannot check, with a note that says so. A click into a TextEdit text area takes about 0.23 s in place of 0.56 s on a test VM. A click on a button whose press action the hit test used to run, such as a button on a web page, now takes about 0.25 s in place of 0.08 s. Background input is unchanged.

## 0.1.20 - 2026-10-26

- **macOS: a window shot says when its pixels may be stale.** An app may not repaint a window on another Space, as WeChat does not until the user switches there, so a shot of it can show the window as it was before a click that landed. `screenshot {window}` (`desk shot` with `window`) now adds `stale: true` and a `note` when the window is on another Space, or minimized or hidden, read from the window list the call already fetches, with no extra call or capture: the pixels may be stale, so do not conclude from them that an action failed. A window covered by others on the current Space is not flagged: WeChat behind a translucent window repaints, and its shots stay current; WeChat fully covered by an opaque window is untested. Background input to such a window that the driver could not confirm says in `unverified` why nobody sees the window, that the input may have taken effect even if a screenshot looks unchanged, not to send it again, and to confirm its effect by a read-back the agent can trust or by asking the user; this replaces the driver's own note and escalation, which tell the agent to check a screenshot and retry in the foreground. Before, only a window on another Space had a note, appended to the driver's, and nothing said that a window shot may be stale. Neither is an error. Linux and Windows shots are unchanged.
- **Docs: click a live list from a fresh shot.** In an app whose list reorders as messages arrive, such as a chat app, take the shot right before a click at its pixels and confirm the effect after it: a click from a shot taken seconds earlier can land on another row.

## 0.1.17 - 2026-10-23

- **Embedded mode.** An app that ships shuttle inside its own bundle and starts `shuttle serve` itself sets `SHUTTLE_EMBEDDED=1` for `serve` and `mcp`, so the macOS permissions belong to that app ([install.md](docs/install.md#embedding-shuttle-in-an-app)). `serve` then starts the bundled cua-driver with `CUA_DRIVER_EMBEDDED=1`, which raises no permission prompts of its own. `mcp` only connects: when no daemon answers it fails at once with `no shuttle daemon answers at <endpoint>`, and never starts one. Before, `mcp` from a copy of shuttle inside another app's bundle found that app as its own bundle and ran `open -a <that app> --args serve`.
- **Stale driver socket.** Before each start of the bundled cua-driver, the first one and every restart, the daemon removes a socket file at the driver's endpoint that refuses a connect, as one a killed driver leaves; a socket that answers or any other error leaves the file alone. A cua-driver in embedded mode refuses to start over an existing socket file. Windows pipes are unchanged.
- **A click, scroll or drag that names a window takes pixels of that window's shot.** With `window`, `x`, `y` (and `to_x`, `to_y` for a drag) are pixels of the image `screenshot {window}` (`desk shot` with `window`) returns, in the foreground and in the background, on any display and at any scale, so the point an agent picks in that image is the point it clicks. A cropped shot returns `origin`, its top left in the whole window image, and its pixel (`px`, `py`) is (`origin[0] + px`, `origin[1] + py`). A title that matches two listed windows alike, both equal to it or both containing it, is refused for such points, since a shot by that title may show the other window, and a window shot waits for a click, scroll or drag in flight, so the driver maps the click by the read it was made for. Before, they were desk coordinates, the main display's pixels, which an agent had to work out from a window origin that `desk windows` does not give, and which on a Retina main display are not the pixels of a window on a 1x display. Without `window` they stay desk coordinates; `at` keeps desk coordinates with `window` too. A script that passes `window` with desk coordinates now clicks elsewhere: drop `window` or convert the point.
- **macOS: a click after a window shot lands where it is aimed.** `screenshot {window}` reads the window at full size, and cua-driver maps the next pixel click on that window by that read, while shuttle still scaled the click by the smaller image of its own earlier read. On a window wider than 1280 image pixels (on a Retina display, wider than 640 points) a background click, or a foreground click in the window, after a shot of it landed short, at about 0.6 of its distance from the window's top left on a 2113-point TextEdit window. Shuttle now keeps the scale of the shot's read for the next click.
- **`at` without a window reads the window at the point.** `desk at` with neither `window` nor `pid` hit-tests the topmost app window the driver lists at the point, and the allowlist judges that window's app; with no app window there it fails with `no app window at the point`. Before, it hit-tested in the front window, so with an allowlist a point on another window failed with the front app's name (`Warp is not in the app allowlist` for a point on a window of an allowed app on a second display).

## 0.1.16 - 2026-10-22

- **Bundled:** cua-driver v0.38.0-loomhand.1 (was v0.37.0-loomhand.5), the fork's patches rebased onto upstream cua-driver 0.38.0 and later fixes: Windows `list_windows` leaves out the driver's own overlay windows, keys for a popup a Linux MPX click opened go through the master keyboard of the session that clicked, and the macOS background gate and window-change detector enumerate windows without the Space snapshot, now upstream ([#5566](https://github.com/trycua/cua/pull/5566), [#5652](https://github.com/trycua/cua/pull/5652), [#5712](https://github.com/trycua/cua/pull/5712)); upstream also tracks the agent cursor's placement explicitly, so negative display coordinates no longer read as an unplaced cursor, keeps a Windows foreground drag off the window that covers its target, and keeps GNOME element actions inside the requested window. `verify_hit`, the kitty AXValue route, the off-Space window lookup, the macOS overlay tile and the X11 core-focus bounce carry over unchanged.

- **macOS: a snapshot or find by title picks the on-screen window over its hidden twin.** Among windows of the same title, none of them active, `snapshot`, `find` and the other verbs that pick a window by the accessibility tree take the newest one on a display before a minimized or hidden one, so `snapshot` of WeChat's "微信" reads its main window and not the hidden 280×380 one beside it. A window shows when its accessibility frame is the bounds of an on-screen window of its process, read from the window list each window listing already reads and from its position and size in the existing batched read. An app's only window of a title, such as a minimized one, can still be picked; two windows with the same frame both count as shown.
- **`shot` of a window on any display.** `desk shot` and the `screenshot` tool take `window` and return that window alone as cua-driver captures it, so a window on a second display, which the main-display capture does not hold, can be shot; `x`, `y`, `w`, `h` then crop the window's image in its own pixels. The window is picked as `focus` picks it, within the app allowlist. A rectangle off the main display still fails, and the error now says to name the window. A device shot refuses `window`.
- **macOS: a title picks the on-screen window over its hidden twin.** Background input, `focus` and the element click by title or pid no longer pick an app's hidden window that is off screen on the current Space when a window of the same app and title is on screen: WeChat keeps a hidden 280×380 "微信" beside its main window, and a click by title went to the hidden one and failed with "this window takes no pointer input without the foreground". An app's only window with a title, such as a minimized one, can still be picked, and twins across Spaces are still refused.
- **`gui_plan` names a front app that stopped answering.** On Linux, when no window is in front because the app of the X active window lists no window in AT-SPI (LibreOffice while it saves or reloads, an app whose accessibility peer hangs), a step that names no window stops with `front app "<app>" (pid N) is not answering accessibility` in place of `no focused window`, and an escalation without a front window shows that line as its outline. The new desk verb `unanswered` gives that window. It is read only when a plan stops.

  - the UI line protocol gains `tap X Y` and `key CODE`, each answered `true` (both events accepted), `false` (one was not, and the press may still have happened) or `unavailable` (nothing could be injected);
  - `unavailable`, a server that predates the requests and a server that does not start leave the call to `adb shell input`, the first two for good; a `false`, an error or a lost reply is an error that says the press may have reached the device, and is never repeated by adb;
  - a tap or key takes 0.6–1.4 ms against 16.5 ms and about 85–90% less CPU on redroid 16;
  - key combinations, swipes and long presses stay on `adb shell input`: a swipe the server injects flings about 1% farther than `input swipe`, enough to move a list off a saved position over repeated scrolls.

  - a capture takes 30 ms against 92–104 ms and about 55–60% less CPU on redroid 16;
  - an uncropped `desk_shot` returns that PNG as it is, with no decode and re-encode; a cropped one is cut as before.
- **Android press scrolls the element into view.** `press` on an element in a scrolling list that is off the screen first asks the element to scroll itself into view (`ACTION_SHOW_ON_SCREEN`, through a `show ID PATH` request of the UI server) in place of a 600 ms swipe and a 400 ms settle:
  - a scrolled press takes 138 ms against 1073 ms for one scroll and 137 ms against 4278 ms for three or four, on the Settings list of redroid 16;
  - the tree is read again after the request; an element that did not move, an element that refused, an error, or a server that predates the request leaves the press to the swipe and settle as before, and a press asks once;
  - lists that do not honour the action, Compose among them, were not tried; they fall back to the swipe.
- **Graceful run ends.** On macOS and Linux a run's timeout, a stop or a dropped client sends SIGTERM to the run's process group, so a script can release the keys it holds or close what it opened, and SIGKILL to whatever is left 2 s later; on Linux the apps the desk moved into scopes of their own are spared, as the bundled driver's end already spared them.   - the daemon starts it with itself in a process group of its own, hands it a socket in a 0700 directory beside its endpoint (`SHUTTLE_SERVICE_SOCKET`), and starts it again with a backoff from 1 s to 30 s when it exits;
  - for a call of one of its tools, the daemon reads the first frame, writes it unchanged to the service's socket and copies bytes both ways until the service closes, with no desk turn and no deadline; about 20 µs added per call at p50 on an Apple M2 Max;
  - `cocoon-shuttle mcp` lists its tools with their schemas, except those with `mcp: false`, and forwards their calls;
  - a stop refuses new calls and closes those in flight, and the service keeps running; `script_run = false` does not turn services off, so the guard rails hold only with no service installed ([docs/safety.md](docs/safety.md#service-plugins));
  - unix only: Windows skips service files with a log line.
- **Android over adb.** With an `[android]` section ([docs/config.md](docs/config.md#android-over-adb)), the daemon drives one Android device instead of the desktop. The device is reached from a Linux or macOS host, and the `shuttle-android` crate holds the backend:
  - the desk verbs answer from the device's UiAutomation tree, through a UI server the daemon pushes and runs under `app_process`;
  - input goes through `adb shell input`, screenshots through `screencap`, and text through a scrcpy clipboard paste;
  - `scroll`, `drag` and `still` answer `unknown desk tool`;
  - the daemon starts no cua-driver, indicator or stop hotkey;
  - `desk computer_state`, `desk computer_act`, `desk computer_end` and `desk look` answer from the command line only; state, act and look write their screenshot to a file, and `computer_end` forgets a session's element indexes;
  - `desk computer_act` is a desk action: `confirm` and the turn apply to it;
  - `launch` takes only package and component names;
  - an `[android]` section with a nonempty `[safety] apps` fails to load, since the device desk enforces no allowlist yet.
  - the screen size comes from `wm size`, read once (restart the daemon after an override), in its natural orientation: a portrait phone turned sideways gets swapped `screen` axes, the portrait default `shot` crop, full-screen windows listed as dialogs, and portrait-sized scrolls and list swipes, while taps and swipes at absolute points pass through; `su` is optional, and without it the paste runs as adb's shell uid, which takes the upstream scrcpy server.
  - an element is tapped in the middle of its part inside the lists that scroll it and the screen, so a row half under an app's own toolbar is tapped where it shows; a row clipped away is off the screen: `computer_state` leaves it out and `press` scrolls to it;
  - the UI server connects UiAutomation with `FLAG_DONT_SUPPRESS_ACCESSIBILITY_SERVICES`, so accessibility services the user enabled stay bound while it runs; before, Android unbound all of them for the whole session.

  The linux archives carry the UI server as `android/cb-ui.jar`, built in the release from `android/ui` with a pinned JDK and checked byte for byte across two builds; an `[android]` section without `ui_jar` takes that jar.
  - a UI server that exits before it prints `ready` is reported with its exit status, the last 4 KiB of its stderr and the last `cb.Ui` abort message in the device's crash log buffer, labelled as possibly from an earlier start (a wrong `ui_jar` gives `ClassNotFoundException: cb.Ui`), or `see adb logcat` when there is none;

  Tested on redroid 16; a stock phone is untested.
- **Shared endpoint.** `[daemon] socket_group` opens the daemon's unix socket to one group's members (mode 0660, owned by the group) on macOS and Linux; unset, it stays 0600. Every member can then use the daemon as its user does ([docs/safety.md](docs/safety.md#a-shared-endpoint)). The Windows pipe stays with its user, and the setting fails the file there.
- **Run errors.** A `script_run` or plugin report that carries `error` now answers `is_error: true`, with the whole report (logs, stderr) as its text, through the daemon and the MCP server alike; before, a failed run looked like a success to the client.
- **Cancel on close.** A client that closes its connection to the daemon cancels the call it carried: a run's process group is killed as on a stop and the turn frees at once, so an interrupted agent no longer leaves a plan holding the turn for up to 110 s. A client must keep its side open until the reply ([docs/wire.md](docs/wire.md#framing)).
- **Android fixes.** A tap lands in the part of an element that its scrolling lists and the screen show, so a row under an app's toolbar or a carousel row inside a list no longer taps the bar over it. Other accessibility services stay bound while the UI server runs.

## 0.1.0 - 2026-10-18

The first usable release: shuttle drives the desktop on macOS and Windows.

- **Daemon.** `cocoon-shuttle mcp` starts `cocoon-shuttle serve` on the first tool call other than `status`, which the MCP server answers itself (on macOS from `Cocoon Shuttle.app`, so the permissions go to the app). The daemon runs the bundled cua-driver on a socket of its own, restarts it when it exits and stops it with itself; desk actions run one at a time.
- **Tools.** `desk` (windows, wait, snapshot, find, read, press, act, at, key, type, click, focus, close, launch, shot, screen), `screenshot`, `gui_plan` and `script_run` now run on macOS (AX) and Windows (UI Automation). `gui_plan` runs whole GUI plans, saves passing ones as flows and replays them; `script_run` runs a module on the bundled Node with the desk API. On Linux the `desk` and `screenshot` tools and the desk calls of a plan or script answer that there is no desk backend yet (P3); `script_run` and model calls run.
- **Models, bring your own key.** One OpenAI-compatible endpoint and key, OpenRouter by default: chat completions for `ask`, `ground`, `decide` and `verify` over chat, and the decisions endpoint for `decide` and `verify`. The key comes from `config.toml` or an environment variable; scripts run without it in their environment.
- **Safety controls on macOS and Windows.**
  - `cocoon-shuttle stop` / `resume`, a global kill hotkey (⌃⌥⌘⎋ on macOS, Ctrl+Alt+Shift+Esc on Windows) and the indicator's Stop and Resume. Stop kills the running plan or script and ends the calls in flight; no MCP tool or plan step can resume.
  - An indicator: a menu-bar item on macOS, a tray icon on Windows.
  - Confirm mode: `confirm = "coordinate"` asks before a click at a point, `"every"` before every desk action. While a dialog is open, every other desk call fails.
  - An app allowlist (`[safety] apps`) that checks every desk call by window, element and point, and blacks out other apps in screenshots.
  - `[tools] script_run = false`; a `config.toml` that fails to load fails every tool call except `status`.
  - These are guard rails for tool use, not a sandbox; they hold only with `script_run = false`. [docs/safety.md](docs/safety.md) lists the limits.
- **Speed.** Batched macOS window lists, process-scoped window reads, the menu bar only in snapshots that need it, a plan step that reuses the plan's snapshot, a window wait in the daemon (`desk wait`) instead of polling, a 1 ms cursor glide, and a grounded click that takes at most 3 screen captures.
  - A plan whose last step is a shifted character such as `shift+a`, an arrow key (with or without shift) while a plain window is in front, or typing without a newline ends without the end-of-plan window wait; Tab and shift+Tab keep it.
  - The macOS window list skips the bundled cua-driver's own windows instead of reading them.
- **Fixes.** On Windows a dialog inside its window's tree, such as Notepad's unsaved-changes prompt, shows in `desk snapshot` and `find` and can be pressed; before, the walk skipped it.
- **Bundled:** cua-driver v0.36.0-loomhand.4 and Node.js 24.22.0, both checked by sha256 at build time.
- **Docs:** a first-time setup in [docs/install.md](docs/install.md) (install, macOS permissions, your key, the safety settings to start with), and the status of every platform.
