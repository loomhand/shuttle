# Changelog

## Unreleased

- **`gui_plan`: a step whose op is not a string is refused before anything runs.** A step such as `{"wait": 2}` threw `TypeError: s[k]?.includes is not a function`; the plan now returns an escalation that names the step and the key, as for a step with two ops.
- **`gui_plan`: a terminal confirms a typed line that ends in a space or a tab.** Since 0.1.47 a terminal's read-back has to show the typed text exactly, so a line typed as `ls ` that the terminal showed as `ls`, or a trailing tab it expanded, stopped the plan with "did not show" before its Return. The trailing space or tab is no longer required to show.

## 0.1.47 - 2026-11-10

- **`gui_plan`: a terminal confirms typed text only with its spaces and case.** The read-back that confirms a background type into a terminal dropped whitespace and case, so a terminal that showed `echohello` or `echo HELLO` confirmed `echo hello`, and the plan sent its Return. It now drops only the line breaks a terminal wraps into a long line.
- **Validation:** runtime unit tests and CI on every platform; no new hardware run.

## 0.1.46 - 2026-11-10

- **`gui_plan`: a terminal that shows part of a typed text stops the plan.** Since 0.1.45, a background type into a terminal that the driver could not confirm let the plan go on, under `background` as under `auto` input, even when the terminal's screen showed part of the text, so a following `{key: "Return"}` ran a partial command line. The plan now goes on, with the step unverified, only when the terminal's screen did not change, as at a `read -s` prompt; a screen that changed without showing the whole text stops the plan with "did not show", and a screen that shows the whole text confirms the step. The driver recognizes Terminal, iTerm2, Ghostty, WezTerm, kitty, Alacritty, Warp, Hyper and Zed's embedded terminal; others, such as VS Code's integrated terminal, Tabby and Rio, are not recognized, and a type into them is handled as in any other window, so under `auto` text they did not show can be typed once more in the foreground.
- **A typed line a terminal did not confirm gets no Return.** A background `type` with several lines pressed Return before each later line whatever the driver said about the line before it, so `echo hello\n` that landed as `echo he` ran `echo he`. On macOS the desk now ends the call before that Return with an error that names the line. A background `gui_plan` type of several lines now types its first non-blank line alone, after a Return for each blank line before it. When the reply names a terminal, it types the rest one line at a time; after a line the terminal did not confirm, it compares the screen with the one it read before that line, once two reads agree within 300 ms of the Return, and presses the next Return only when the screen shows the line or did not change, so `read -s pw` followed by a password at its prompt submits each once, and otherwise stops the plan with "did not show" naming the line. A terminal step is confirmed or left unverified by its lines, not by a whole-text read that a prompt between them would break, and a terminal note is the step's note even after a Return's. The terminal path costs about 86 ms a line, two reads of the screen before each later line (+257 ms on a 3-line step); elsewhere the rest of the lines go in one more call per step with no extra read, at no measurable cost (+59 ms on a 10-line step, +122 ms on 50 lines, within noise), unless the text starts with blank lines: then each blank line's Return is sent first and the screen is read once it settles. A line that is only a carriage return counts as blank. The `gui_plan` check also reads the end of a field's text when its tree value, cut to its first 200 characters, may hide the end where a terminal takes input: one more read per such field before each background `type` and one more after a type the driver could not confirm. Under `auto` a field read only in part never leads to typing a step again in the foreground: an insert near the start of a long Windows field leaves its end unchanged.
- **`read` with `tail` returns the end of a long text.** A `read` with `text` returns at most 65,536 characters, the first ones; with `tail: true` it returns the last ones, and the reply says `truncated: true` whenever the text was cut. This holds on Android, whose `read` returned the whole value, and on Windows for a document read through its text pattern: a tail read moves back by lines until it holds more than the limit or reaches the start, and a head read asks for twice the limit in UTF-16 units, so a text with characters outside the Basic Multilingual Plane is flagged as cut when it is. A Terminal window with unlimited scrollback passes that limit after about 7,000 lines, and input lands at its end.
- **macOS: an unconfirmed type into a terminal is not advised to go in again.** The bundled driver told a caller to send a terminal type it could not confirm once more in the foreground; at a prompt without echo, such as `read -s`, a screenshot never shows the text, so an agent that followed the advice typed it twice. The driver now answers that a terminal may not echo what it reads and that the text must not be typed again, with no foreground advice.
- **macOS: an accessibility insert whose field changed the text is not typed again as keys.** The driver followed such an insert with the same text as key presses, which could type it twice; it now answers it unverified.
- **macOS: a typed field that stops changing without growing settles in 0.5 s instead of 2 s.** The driver waited out its full 2 s read-back window when a field changed without growing; it now answers unverified once the field has not changed for 0.5 s, and still waits for a field that keeps changing.
- **macOS: a terminal type is confirmed only by a copy of the text the terminal did not already show.** A terminal's text holds its scrollback, so the bundled driver confirmed a command typed again, such as `git push` already on screen from an earlier run, when only part of it landed (`git pu`), and a plan's next Return ran the partial command. The driver now confirms a terminal type only when the screen holds more copies of the text than before it, and answers unverified when it cannot read the screen before typing, so `gui_plan` checks the screen itself. Typing into other fields is confirmed as before.
- **Bundled:** cua-driver v0.45.1-loomhand.6 on every platform (was v0.45.1-loomhand.4).

## 0.1.45 - 2026-11-10

- **macOS: text typed into a terminal that does not echo it goes in once.** The bundled driver sends text in batches and read the terminal's screen back to count what landed. A prompt without echo, such as `read -s` for a password, leaves the screen unchanged, so the driver counted nothing delivered, typed the whole text again about 500 ms later and answered that 0 characters landed, to be retried from the start. A background `read -s` given "abc" read 6 characters; it now reads 3, and the call answers `unverified` instead. The driver now retypes the rest of a text only when a native field shows its old value followed by the start of the text, never into a terminal, and a terminal's screen counts only when it shows the whole text; a field that took scattered characters of a batch, or whose text changed without growing (a selection replaced), is reported unverified instead of retyped or retried from the start, after the driver has waited for the text to show. Every terminal reply now names the terminal emulator, kitty's included. Foreground typing, TextEdit and a secure password field type as before.
- **`gui_plan`: a background type into a terminal is not typed again in the foreground.** Under `[desk] input = "auto"`, a type whose text a terminal did not show, such as a `read -s` password, was typed a second time in the foreground. A terminal type the driver could not confirm now stays unverified in the plan's result instead. The check reads the bundled driver's "terminal emulator" detail in its reply, so it follows the pinned driver.
- **Bundled:** cua-driver v0.45.1-loomhand.4 on every platform (was v0.45.1-loomhand.1).

## 0.1.44 - 2026-11-10

- **`gui_plan` reads one window list fewer per settling step.** After a click, menu or close step waits for the window to settle, the next step and the end of the plan take the list that wait read, when it is under 25 ms old, shows a front window and no other call came after it; a macOS list costs 11-15 ms.
- **The daemon listens before its model client is built.** It builds the model client while the rest of it starts, after it binds its socket, and a call that starts the daemon checks for it every 10 ms instead of 100. On a macOS guest the first answer after a cold start came 27-54 ms sooner in most runs; on Windows it was unchanged.
- **macOS background typing reaches a Chromium app again.** The bundled 0.45.1 driver sends background text as key events that carry several characters, and a Chrome that has been in front once drops them all. Background typing into a Chromium or Electron app now asks the driver for 1 ms a character: 0 of 9 to 9 of 9 runs of 620 characters on a long-running Chrome, at about 11 ms a character. Safari, Terminal and TextEdit keep the driver default. Characters outside the Basic Multilingual Plane, such as most emoji, still do not reach such a Chrome in the background, as with v0.1.43; the call fails and says how much landed, and foreground typing carries them.
- **Linux: the driver's cursor overlay no longer slows every key or opens a phantom menu.** With `[driver] overlay = true`, the default, cua-driver keeps a full-screen override-redirect window mapped that names no process; shuttle counted it as another app's popup, so every `computer_act` key took the slower per-window route with a session restart after it, and the overlay's first mapping was reported as "menu opened". The window list now leaves the overlay out in the same request that reads it: 713 to 169 ms a key with the overlay on, where the rest is the screenshot after each action, which comes from the driver while the overlay shows so that it leaves the agent cursor out.
- **Element ids of one snapshot all resolve.** Once the id map reached its cap, it was cleared in the middle of a snapshot (Windows) or kept only window ids (macOS), so ids handed out earlier in the same snapshot answered `unknown element id`. The map is now trimmed only when a snapshot, a find or a lookup at a point starts, before it hands out any id; a window listing or an action inside a press trims nothing.
- **A desk call that times out before it starts frees the desk at once.** An action queued behind a hung accessibility read kept its turn until that read returned, so every other action answered "desk busy" while nothing ran.
- **A background element click lists the windows once.** It asked the driver for the window list twice, one driver round trip more per click.
- **`gui_plan`.** A `wait` step no longer asks the model about a window that only changed its title, such as Notepad gaining a `*` after a save, which failed the wait before the dialog came, or failed it outright with no model; a background type reads the fields of its window four at a time instead of all at once; a `verify` with a `role` reaches elements of that role outside the interactive ones, such as a document body; a state check crops its control relative to the screen origin; one flow file without `saved_at`, `params` or `steps` no longer breaks every later save.
- **Scripts: `desk.key` and `desk.typeText` pass `app`.** The daemon takes `app` for both, but the runtime dropped it.
- **Android: a scroll's `amount` is capped at 50 swipes**, as the desk driver caps its notches; `amount: 1000` ran about 1000 swipes.
- **Android: the menu-bar indicator stays off after a bad `kill_hotkey`.** A kill hotkey that did not parse reset the safety settings after the indicator was turned off for a device host, so the indicator came back.
- **Windows install keeps `%VAR%` entries in your PATH.** `install.ps1` read the user PATH expanded and wrote it back as a plain string, which froze entries such as `%USERPROFILE%\bin`; it now reads and writes the raw value as an expandable string and tells running apps that PATH changed.
- **Bundled:** cua-driver v0.45.1-loomhand.1 on every platform (was v0.43.1-loomhand.2), the fork's patches rebased onto upstream cua-driver 0.45.1. Typing is sent in batches instead of one key at a time: 620 characters into a background Terminal take 0.9 s instead of 26.7 s on macOS, 2000 ASCII characters take 1.1-1.6 s instead of 21 s on Linux, and the Windows key fallback is 2.6x (SendInput) to 15.6x (PostMessage) faster; a text field that never takes the text answers `unverified` after 0.7 s instead of 4 s. On Linux, characters typed through a borrowed keycode (CJK, for example) are paced and the keycode stays bound until 150 ms after the last of them, so xterm, Tk and Qt apps keep them under batched typing; this costs about 20 ms per such character plus up to 150 ms per text (a 15-character CJK line into mousepad takes about 0.5 s, about 1 s over the virtual keyboard). The virtual keyboard waits for the X server to read each run of about 8 key events, so batched typing loses no keys under load. On macOS the keyboard-layout read that crashed the driver (#290) is now upstream's fix.

## 0.1.43 - 2026-11-09

- **Each MCP session is its own caller** (#317). Every `shuttle mcp` session reached the daemon as the same agent, so two MCP clients shared one `web` hold, and one client turning a page tree off turned it off for the other; they also shared the default computer session and looked the same to service plugins. A session on stdio now calls as `mcp-<client name>-<nonce>` and one over HTTP as `mcp-http-<Mcp-Session-Id>`; the CLI and `gui_plan` and `script_run` runs keep their own ids.
- **MCP results say what they mean** (#316). The server instructions and the `desk` and `gui_plan` descriptions state which desk results sent nothing for their call (declined, a confirm dialog open, desk busy) and which may have taken effect (stopped by the user, `unverified`, a `type` that counts the lines typed before its error, `gui_plan` caveats and what a failed plan left).

## 0.1.42 - 2026-11-09

- **The confirm dialog shows what it allows.** It printed an agent's action names as given, so a name could carry line breaks and words that read as reassurance; it said only how many characters a `type` would type; a click named no window although its point is then in that window's pixels; and a long `computer_act` list was cut off before the step that asked. A name that is not a plain word is now quoted and escaped, a `type` or key step shows its text as an escaped preview with its window, app or process first, a click or drag names its window and modifiers, and a list too long for the dialog says how many steps it leaves out. A password the agent types therefore shows in the dialog on your screen ([safety.md](docs/safety.md#confirm-mode)).
- **Under confirm, an agent's `record_start` asks first.** An agent could start a recording over MCP with `confirm = "every"` and take what you typed and crops of your windows with `record_stop`; the menu's Start recording still starts at once.
- **The app allowlist refuses `launch` arguments that start with `-`, and on Windows `/`.** An allowed Chromium browser launched with `--gpu-launcher` or `--renderer-cmd-prefix` ran any program, which `script_run = false` is meant to rule out; URLs and other plain arguments still pass.
- **`shot` no longer writes a `path`.** `desk shot` and the MCP `screenshot` tool wrote the PNG to any path a caller gave, so a caller of the desk could overwrite any file your user can write. The image comes back in the reply as before; `shuttle desk shot` saves it to a temporary file itself.
- **A stopped or timed-out action no longer runs late.** An action queued behind a slow accessibility read ran once the read returned, even after a stop or after its own call had timed out; it now runs only if its call is still waiting. Callers that time out behind one hung app also restart the accessibility backend once instead of once each.
- **macOS: a click the named window cannot take is refused while another app covers the point.** It fell back to a click at the screen point, which landed on the covering app, possibly one the allowlist leaves out, and reported success.
- **macOS: recordings leave out the blocked apps on every system language.** The blocked list matched the app name macOS shows, which is translated, so on a German Mac System Settings, Keychain Access and Passwords were recorded. A name now also matches the app's bundle name, whatever its case, and keys sent to shuttle itself are left out as its clicks were.
- **macOS and Windows: a kill hotkey that does not register says so.** When another app holds the combination, the Stop entry no longer names the hotkey and a dialog says how to stop shuttle instead.
- **Windows: a pipe passes the client's check only by its owner.** A pipe owned by another user passed when the process at the id Windows recorded for its server ran as you, and that id can be reused, so another local user could take the driver's pipe name first and receive what the daemon types. A pipe now passes only when it belongs to you or, for a driver run elevated, to Administrators.
- **`computer_state` escapes what it reads off the screen.** Element labels, values and window titles went into the reply as given, so a page could write a label that read as more element lines with positions it chose; they are now quoted, escaped and capped at 80 characters (values at 60).
- **cua-driver calls.** A failed input whose message mentioned an ended session started the session again and sent the input a second time; only the driver's own ended-session error does that now. A click whose call was dropped while it ran still spaces the next click near it, so the two do not make a double click.
- **Linux:** connecting to the accessibility bus gives up after 2.5 s instead of holding every call when the bus hangs; a node with no text and no number reads with no `value`, as on macOS and Windows; a node with many cached children no longer costs time in the square of their count.
- **Android:** a `computer_*` call with no `session` takes its caller's own, as on the desktop; the UI server recycles the touch events of a tap.
- **`gui_plan`.** A typed line whose first Return opens an overwrite confirmation sends no second Return into it and stops; a background `wait` that several windows match takes none of them unless one title is exactly the text; a passing plan no longer saves over a flow saved by name from this release on, and its own name stays within 40 characters; a menu shortcut the user declines stops the plan instead of pressing the entry; a flows commit is never signed, so no signing prompt opens after a plan; a screenshot check whose answer is not true or false fails; a step whose only op is empty is refused; under `input = "auto"` a password field is never typed again in the foreground. In drafts of a recording, a character typed with Option stays in its typed text, and a model caption keeps its first line, at most 80 characters.
- **`decide`** takes the likeliest of the question's options when the model's choice is none of them, and fails only when its probabilities name none.
- **Install:** `install.sh` runs from one function, so a download cut off by `curl | sh` runs nothing.
- **Bundled:** Node.js 24.22.2 (was 24.22.0; 24.22.1 was a security release). rustls-webpki 0.103.16, webpki-roots 1.0.11 and tokio 1.54.1 clear RUSTSEC-2026-0382, -0381 and -0386.
- **Windows: a known limit for keys right after a large write** (#258). An app that checks spelling as you type can hold and later replay the keys after a large text write, so on a loaded machine a chord such as `ctrl+s` can land as plain text; [platforms.md](docs/platforms.md#windows) describes it and how to check a chord's effect.
- **macOS: the first run needs no manual restart.** Once Accessibility and Screen Recording were on, screenshots still failed with `direct_capture_consent_required` until the daemon was restarted by hand, and macOS's Quit & Reopen after the Screen Recording switch left the daemon stopped. The bundled cua-driver now lets the first capture show macOS's one-time screen access alert, so screenshots work after Allow, and an app launch with no arguments, as Quit & Reopen does, starts the daemon on the default endpoint. An embedding app (`SHUTTLE_EMBEDDED=1`) keeps owning that alert.
- **Windows: the confirm box stays on top** (#295). After the step before brought another app to the front, the message box opened behind that app with only its taskbar button flashing. It now has an always-on-top owner, so it shows on top until you answer it; it takes the keyboard focus when Windows lets it, else click OK or Cancel. It no longer has a taskbar button.
- **Windows: a `socket_group` member that is another user reaches the daemon** (#303). The client proved the daemon's user by opening the daemon's process, which another user may not do, so every call of a group member failed with access denied. The daemon now owns its pipe as its user and the client reads that owner from the pipe; a pipe that another user serves under the name is still refused.
- **Windows: `shuttle stop` works from an SSH session** (#296). The daemon read a caller's user by opening its process, which an elevated SSH-session process does not allow, so `stop`, `resume` and the recording calls refused the daemon's own user as another one. It now reads the user from the pipe client's token; another user is still refused.
- **Linux: a `gui_plan` step after an accessibility action click waits for the focus to move** (#291). GTK runs a button's accessibility action from a 250 ms timer, so a `type` or `key` step right after such a click, as after New tab in GNOME Text Editor, went to the element that still had the focus. Such a step now waits until that element loses the focus, at most 500 ms after the press; a click whose action moves no focus costs at most about 350 ms more, and a click not followed by `type` or `key` costs nothing.
- **macOS: the confirm dialog gives the front back** (#297). After the dialog closed, no app was active, so keys typed next reached no window. The app that was in front before the dialog is active again whatever the answer; a step that names its window still brings that window to the front itself.
- **macOS: a `gui_plan` menu step finds an entry that retitled itself** (#292). TextEdit renames Format > Wrap to Page to Wrap to Window after use, but its accessibility title keeps the old name until the menu opens again, so a step on the new name stopped with `menu entry "Wrap to Window" not found`. A step whose entry is not in the tree by that name now opens the menus above it once, closes them and reads the tree again before it matches; a step that matches at once costs nothing more.
- **Linux: `computer_state` on one of several Chrome windows lists only that window** (#308). Chrome opens a new window 10 px right of and below the last one at the same size, which the driver took as too close to tell apart, so it read every window of the app: a reply listed the other window's elements at the front window's positions, and a click by index could land in the other window. The bundled cua-driver now takes the one frame that matches the window exactly; two windows at the same place and size still read the app as a whole.
- **Windows: `type` on a busy machine no longer garbles the text** (#309). When the target did not answer the focused-document write within 200 ms, cua-driver typed the text as keys instead, and Notepad, which replays keys while it is busy, turned it into runs of one character with half of it lost (13 of 800 throttled runs). The bundled cua-driver now waits up to 2 s for that write and, if the target still does not answer, returns an error that says nothing was written instead of typing keys; a write that answers in time is as fast as before.
- **Bundled:** cua-driver v0.43.1-loomhand.2 on every platform (was v0.41.2-loomhand.1), the fork's patches rebased onto upstream cua-driver 0.43.1. On macOS `press_key` no longer crashes the driver (SIGILL) once the driver has been the active app (#290). Its permission guide names Shuttle, the app System Settings lists, instead of "Cua Driver", in the window, the drag tile and the terminal lines, and opens at the left of the screen instead of over System Settings' switches and macOS's own access prompt. From upstream 0.42 and 0.43: on macOS window reads and background actions look up one window instead of listing every window, and an element click on a web text field waits for the field's focus instead of a fixed 800 ms (107 ms instead of 831 ms median on a test Mac) and focuses a Safari text area so the next text lands in it; on Linux non-ASCII text typed into GTK 3 and Qt fields is no longer cut off, a background write into an app with several editable fields and none focused goes out as key events instead of into the first field, and `computer_state` with the pid of an app whose only window is minimized reads that window instead of failing; on Windows UI Automation walks no longer fail when another component in the process already set up COM.

## 0.1.41 - 2026-11-08

- **Link nodes carry their URL.** `desk` `snapshot` and `find` with `urls: true`, and `read` always, give a `link` node `url`, its target, on Linux, macOS and Windows, so the permalinks of a feed's posts come from one snapshot instead of one `read --web` per link on macOS only. The text outline leaves it out. On Windows a link's `read` carries its target in `url` instead of `value`, and a `gui_plan` `verify` with `value` on a link compares that target on every platform ([wire.md](docs/wire.md#desk-calls)).
- **Windows: a menu shortcut whose input stalled stops the plan.** When `gui_plan` chooses a menu item by its shortcut and cua-driver answers `input_delivery_stalled` (the keys went in but the target had not read them yet), the plan now stops and reports it instead of also invoking the menu item, which could run the command twice, such as a second Undo. Other shortcut errors still fall back to invoking the item.
- **Windows: foreground `type` sends each line as one text.** It typed one key per character, so a long text lost the shift on some capitals and dropped characters: a 2000-character text into Windows 11 Notepad lost 120 capitals and 25 characters a run. Each line now goes to cua-driver as one text, typed as Unicode and independent of the keyboard layout; background `type` still sends keys.
- **Windows: foreground keys and `type` with only a window title bring that window to the front first**, as on macOS, and fail naming the window that stayed in front. Before, they went to whatever window was in front and reported success, such as text typed into the Search box instead of a Notepad started behind Explorer.
- **macOS: an app step with `url` opens the page in Safari.** `{app: "Safari", url}` in `gui_plan`, and `desk launch` with `args` that hold no option, now hand the URLs to the app as `open -a` does, so a running app opens them and no second instance starts. Before, the URL was a command-line argument of a new instance: Safari showed "Safari Can't Open the Page" and the step failed with "Safari shows no window at <url>". `args` with an option, such as a Chrome profile, still start a new instance.
- **Linux: `computer_act` foreground typing brings the target window to the front first**, so the driver's focus restore leaves the keyboard focus on it. With the bundled driver on X11, a foreground `type` aimed at the topmost app window while another window held the focus typed into the target and then gave the focus back to the other window, so the next key went there, while every call reported success.
- **A hung app's windows stay listed, marked `stale`, on macOS, Windows and Linux** (#254, #255, #281). On macOS that state outlives a backend restart after a call past its limit, as on Windows. A window whose app stops answering keeps its last frame with `stale: true` instead of leaving the list; on Windows one WM_NULL probe of at most 500 ms per thread decides it, in place of leaving out a window Windows marks as not responding. A stale window is active only while its app is in front, so a plan sees a hung front app and stops. On macOS a hung front app stays the front without being asked, so a window list no longer waits 500 ms on it (#277).
- **`gui_plan` stops at an app that stopped answering** (#251). An app step escalates on a stale window instead of launching the app again, a step whose front window is stale waits up to 2 s for it and then escalates, and an AT-SPI call to an app that left the bus says the app exited or crashed. A LibreOffice Calc window lists its menu bar once, so a click no longer finds three matches of each menu entry.
- **Key names** (#272). Linux, macOS and Windows take one alias table, the plus key is `+` on all three, and a name that is no key of the drivers fails before any input; before, Windows pressed the first letter of an unknown name, so `arrowup` pressed A. `delete` is the forward Delete key on macOS too.
- **macOS window ids are window numbers** (#276), the same on and off the current Space, so a background plan keeps its window when the id cache fills or the window moves to another Space. Sheets and windows without a number keep `pid/n` ids.
- **`shuttle desk` keeps `id` and `window` values as strings** (#275), so `desk snapshot id=21` no longer sends the number 21.
- **Desk input.**
  - A desk `type` waits as long as the driver may spend typing the text, instead of 30 s whatever its length, after which the driver typed on into whatever window was in front (#278).
  - A desk click waits out the click spacing on every OS, so two desk clicks at one point no longer make a double click on Windows (#279).
  - `press` and `act` hold the input turn through the element click (#264), and on macOS a menu-item click that outlives its call limit holds it until the press ends. A computer action or launch that waits for the turn answers busy after 15 s, as a desk action does (#263).
  - A `press` clicks at negative desk coordinates, on a display left of or above the main one.
  - A foreground `click`, `scroll` or `drag` with `window` brings that window to the front first, as `key` and `type` do, so a covered point no longer reaches the window on top while the call reports success.
  - A `delivery_mode` the desk does not use is refused at once, not after the 15 s turn wait.
  - Two first holders of a page tree no longer leave it on after the last release (#263).
- **Windows.** A press on a hung app holds the turn about 20 s instead of about 60 s (#280). A menu toggle read by pixels reads the entry in the menu the step opened and closes it after; in the background it refuses with no menu left open (#282). A second open of the tray menu no longer closes at once.
- **Linux.** An AT-SPI tree read that finds its app hung fails with "not responding" instead of returning a partial tree. A call that never reached cua-driver no longer waits out a second 10 s connect to end its session (#269). The typed settle reads its fallback tree inside the settle deadline (#273).
- **Replays.**
  - A step whose target or window holds a `{{param}}` is never pinned by a stored fingerprint or recorded title, so a replay with another value no longer clicks the recorded element.
  - An app step with `title` waits for a window of that title instead of taking any window of the app.
  - In the background, a recorded `after` takes the new top-level window of the plan's app that the step opened (#271).
  - `desk.at` sends whole pixels, a type step into a password field no longer quotes the secret in its error, and a background menu toggle that needs pixels refuses before it opens the menus (#262).
  - A recording's draft keeps the keys F1 to F12.

- **computer_act clicks on text fields on macOS and Windows.** A left click on a text field element (`AXTextField`, `AXTextArea`, `AXComboBox`, `Edit`, `ComboBox`) asks the bundled cua-driver for a `verify_hit` click, which v0.37.0-loomhand.5 delivers: the driver brings the field's window to the front and posts a click at the field's centre only when the accessibility hit test there finds that same element or one inside it, so typing next goes into the field. Before, the click ran the field's press action, which does not focus it on macOS, or a background click on Windows, and the text went to whatever window was in front. When the driver refuses (another element on top, the field gone or replaced, no foreground), the field gets its press action, and if it has none the refusal is returned rather than a click at a point; a click that failed after it was sent is not repeated. A cua-driver without `verify_hit`, such as an older one at its default socket that a build without a bundled driver uses, presses the field as before.
- **Grounded clicks need an element and a clear yes.** When a `gui_plan` click finds no element and grounds the target on the screen, it clicks only where the accessibility tree has an element under the point that is not a root (a `window`, `frame`, `application`, `dialog` or `document`, which macOS `AXWebArea` and UIA Document map to) and lies inside the plan window or a window it owns, judged by the element's ancestors when they name a window (a Windows UWP app shows its content from another process than its frame's) and by its process when they name none; otherwise it refuses and asks no verification model, with `grounding pointed at no accessible element`, `…, a window or document root`, `…, which belongs to another process`, `…, whose process is unknown` or, when the element under the point could not be read, `… a point whose element could not be read: <reason>`. `desk.at` now returns the `pid` of the element it finds. So `gui_plan` no longer clicks by vision alone in an app that exposes no accessibility tree, such as desktop Chrome on a cocoonbox desktop: use `computer_act` there. The first check of the 640x400 crop now takes the click alone only at p ≥ 0.9 (was 0.5); below that the zoom check (0.65) and the screen check with a ring (0.95) decide. A control that was not on a Chrome page got a grounded click in about 1 run of 7 before, at crop answers of 0.43–0.58 for a point with no element under it. The step's `trace` entry now carries `ground` with the check path, `p`, `p_zoom`, `p_full` and the element under the point (`hit`), whether the step clicked or refused.

## 0.1.9 - 2026-10-20

- **Background input.** `[desk] input = "background"` sends desk input to its target window through cua-driver without fronting it or moving your pointer: keys, typed text, scrolls and drags go to the window that `window` or `pid` names, a click at a point goes to the window under it or the one named, and a press or element click goes to the element's own window even under another window. It never falls back to the foreground; an action that needs it fails and names why, `focus` is the one call that fronts a window, `gui_plan` and the Linux computer actions refuse, and results the driver cannot confirm carry `unverified`. On Windows a background press clicks in the element's own window, and UI Automation focus, select and action refuse, since they front it. `foreground` stays the default, and `auto` acts as it for now ([config.md](docs/config.md#desk-input), [safety.md](docs/safety.md#background-input)).
- **Desktop clicks after a capture.** On macOS and Windows a desktop click after a `still`, a `shot` or a settle lands on the point asked: the desk's own captures run in a driver session of their own, since the driver reads desktop x,y as pixels of the session's last capture; a click after a still landed 4x off at 1x and 8x off on a Retina Mac. `screen` reports pixels on a Retina Mac, as the wire says; it reported points, which halved `gui_plan`'s grounding and crop fitting there.
- **Linux typing through XTest.** On Linux `computer_act` types a desktop-routed line on the core keyboard through XTest, as `desk type` does, instead of through the driver at 10 ms per character: a 40-character line takes about 80 ms in place of 470 ms. A line the keyboard map cannot type goes to the driver as before, an XTest error fails the action without a driver retry, and a stop ends the typing at its next key.
- **Android taps and keys from the UI server.** A tap and a single key press are injected by the UI server through `InputManager`, as `adb shell input` does it, in place of an adb process and a device JVM per call:
  - the UI line protocol gains `tap X Y` and `key CODE`, each answered `true` (both events accepted), `false` (one was not, and the press may still have happened) or `unavailable` (nothing could be injected);
  - `unavailable`, a server that predates the requests and a server that does not start leave the call to `adb shell input`, the first two for good; a `false`, an error or a lost reply is an error that says the press may have reached the device, and is never repeated by adb;
  - a tap or key takes 0.6–1.4 ms against 16.5 ms and about 85–90% less CPU on redroid 16;
  - key combinations, swipes and long presses stay on `adb shell input`: a swipe the server injects flings about 1% farther than `input swipe`, enough to move a list off a saved position over repeated scrolls.
- **MCP cancellation.** `cocoon-shuttle mcp` keeps reading its client while a request runs, and a `notifications/cancelled` drops the request it names, running or queued, without a reply; a running one closes its daemon connection, where the daemon ends the call. Before, the server read the next line only after the call had ended, so an interrupt reached it up to the 110 s run limit late while the desktop kept acting.
- **Android screenshots from the UI server.** `desk_look`, `desk_shot`, `computer_state` and every `computer_act` take the screen from the UI server's `UiAutomation.takeScreenshot` in place of an `adb exec-out screencap -p` process:
  - the UI line protocol gains a `shot` request answered by a binary frame, `png N` and then N bytes before the end line; a server that predates it answers a dump, and `screencap` serves for good after that, as it does for one call after a failed shot;
  - a capture takes 30 ms against 92–104 ms and about 55–60% less CPU on redroid 16;
  - an uncropped `desk_shot` returns that PNG as it is, with no decode and re-encode; a cropped one is cut as before.
- **Android press scrolls the element into view.** `press` on an element in a scrolling list that is off the screen first asks the element to scroll itself into view (`ACTION_SHOW_ON_SCREEN`, through a `show ID PATH` request of the UI server) in place of a 600 ms swipe and a 400 ms settle:
  - a scrolled press takes 138 ms against 1073 ms for one scroll and 137 ms against 4278 ms for three or four, on the Settings list of redroid 16;
  - the tree is read again after the request; an element that did not move, an element that refused, an error, or a server that predates the request leaves the press to the swipe and settle as before, and a press asks once;
  - lists that do not honour the action, Compose among them, were not tried; they fall back to the swipe.
- **Graceful run ends.** On macOS and Linux a run's timeout, a stop or a dropped client sends SIGTERM to the run's process group, so a script can release the keys it holds or close what it opened, and SIGKILL to whatever is left 2 s later; on Linux the apps the desk moved into scopes of their own are spared, as the bundled driver's end already spared them. A run whose client goes away during that grace is killed at once, and so is every run still in its grace when the daemon shuts down. Before, the group got SIGKILL at once. Windows keeps ending the run's Job object at once.
- **Known issue:** on a Retina Mac guest whose apps answer accessibility slowly at launch, a just-launched app can drop out of `windows` for 10 s, longer than the app step's 8 s wait, and the step fails with `has no window`; 1x guests are not affected.

  - `gui_plan`'s outline note tells a backend node cap from a text cut and points to `desk snapshot` or `find`, not to tools shuttle does not have; an outline at exactly the text budget gets no note.
  - `desk focus` fails on a window id that is not a number instead of sending a null id.
- **Speed.** `gui_plan` reuses a window list where no desk action runs before the next read, and the desk skips work whose results it never uses.
- The `gui_plan` run log starts over once it passes 1 MiB.

## 0.1.0 - 2026-10-18

The first usable release: shuttle drives the desktop on macOS and Windows.

- **Daemon.** `cocoon-shuttle mcp` starts `cocoon-shuttle serve` on the first tool call other than `status`, which the MCP server answers itself (on macOS from `Cocoon Shuttle.app`, so the permissions go to the app). The daemon runs the bundled cua-driver on a socket of its own, restarts it when it exits and stops it with itself; desk actions run one at a time.
- **Tools.** `desk` (windows, wait, snapshot, find, read, press, act, at, key, type, click, focus, close, launch, shot, screen), `screenshot`, `gui_plan` and `script_run` now run on macOS (AX) and Windows (UI Automation). `gui_plan` runs whole GUI plans, saves passing ones as flows and replays them; `script_run` runs a module on the bundled Node with the desk API. On Linux the `desk` and `screenshot` tools and the desk calls of a plan or script answer that there is no desk backend yet (P3); `script_run` and model calls run.
- **Models, bring your own key.** One OpenAI-compatible endpoint and key, OpenRouter by default: chat completions for `ask`, `ground`, `decide` and `verify` over chat, and the decisions endpoint for `decide` and `verify`. The key comes from `config.toml` or an environment variable; scripts run without it in their environment.
- **Safety controls on macOS and Windows.**
  - `cocoon-shuttle stop` / `resume`, a global kill hotkey (⌃⌥⌘⎋ on macOS, Ctrl+Alt+Shift+Esc on Windows) and the indicator's Stop and Resume. Stop kills the running plan or script and ends the calls in flight; no MCP tool or plan step can resume.
  - An indicator: a menu-bar item on macOS, a tray icon on Windows.
  - Confirm mode: `confirm = "coordinate"` asks before a click at a point, `"every"` before every desk action. While a dialog is open, every other desk call fails.
  - An app allowlist (`[safety] apps`) that checks every desk call by window, element and point, and blacks out other apps in screenshots.
  - `[tools] script_run = false`; a `config.toml` that fails to load fails every tool call except `status`.
  - These are guard rails for tool use, not a sandbox; they hold only with `script_run = false`. [docs/safety.md](docs/safety.md) lists the limits.
- **Speed.** Batched macOS window lists, process-scoped window reads, the menu bar only in snapshots that need it, a plan step that reuses the plan's snapshot, a window wait in the daemon (`desk wait`) instead of polling, a 1 ms cursor glide, and a grounded click that takes at most 3 screen captures.
  - A plan whose last step is a shifted character such as `shift+a`, an arrow key (with or without shift) while a plain window is in front, or typing without a newline ends without the end-of-plan window wait; Tab and shift+Tab keep it.
  - The macOS window list skips the bundled cua-driver's own windows instead of reading them.
- **Fixes.** On Windows a dialog inside its window's tree, such as Notepad's unsaved-changes prompt, shows in `desk snapshot` and `find` and can be pressed; before, the walk skipped it.
- **Bundled:** cua-driver v0.36.0-loomhand.4 and Node.js 24.22.0, both checked by sha256 at build time.
- **Docs:** a first-time setup in [docs/install.md](docs/install.md) (install, macOS permissions, your key, the safety settings to start with), and the status of every platform.
